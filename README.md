# Kompast

Self-hosted Notion × JIRA for an internal BU: collaborative docs, kanban boards with configurable sprints, automation, and an AI assist layer — one Postgres-backed workspace, not two disconnected tools.

Full architecture, data model, and the phased build plan live in the design doc this repo was scaffolded from (`~/.claude/plans/use-the-claude-design-mcp-snuggly-shore.md` on the machine that generated it). This README covers only what's needed to run what exists today — **P0 through P7 are complete** (foundation/auth, kanban core, docs core, REST API/MCP, sprints/roadmap, notifications/mail, automation, AI assist); **P8 is partial** (a JIRA importer exists end-to-end — extract/map/load plus a REST endpoint and a project-page UI tab to trigger one — but no Notion importer at all) and **P9 (hardening/cutover) is not built yet** — and how to deploy it.

## Stack

TanStack Start (React, SSR, Nitro `node-server`) · Better Auth (Microsoft Entra ID via `genericOAuth`/`microsoftEntraId`, `organization` = workspace, `apiKey` for PATs) · Drizzle + Postgres 17 · Redis · Google Cloud Storage · Tailwind v4 · BlockNote + Hocuspocus (Yjs) for real-time docs · pnpm workspaces + Turborepo.

## Repo layout

```
apps/web      TanStack Start — UI, docs editor, guest share routes, REST API (P3+), MCP server (P3+)
apps/collab   Real Hocuspocus (Yjs) server — per-page signed-token auth, Postgres persistence, periodic version snapshots
apps/worker   BullMQ background jobs — mail outbox (P5) and automation events (P6), each its own queue
packages/core Domain service layer — every mutation lives here once, behind one permission check
packages/ai   AI provider adapter (Anthropic / Azure OpenAI / OpenAI-compatible) — no SDK dep, raw fetch (P7)
packages/db   Drizzle schema, migrations, RLS policies, tenant isolation
packages/ui   Design tokens + primitives, generated from the Claude Design mockup
packages/env  Zod-validated environment — refuses to boot on a missing var
infra/        Dockerfiles, docker-compose.yml, Caddyfile.example, .env.example
```

## Local development

Requires Node 22+, pnpm 10+, a Postgres 17 instance, and a Redis instance reachable at the URLs you put in `.env`.

```bash
pnpm install
cp infra/.env.example apps/web/.env   # fill in every value, see below — infra-level only
pnpm --filter @kompast/db generate    # writes packages/db/drizzle/*.sql
pnpm --filter @kompast/db migrate     # applies it to DATABASE_URL
pnpm dev                              # turbo runs apps/web (:3000) and apps/collab (COLLAB_INTERNAL_PORT) together
```

Docs' real-time editing needs `apps/collab` actually running — `pnpm dev` starts both, but if you're running `apps/web` on its own (e.g. `pnpm --filter @kompast/web dev`), the editor will hang trying to sync until you also start `apps/collab`.

`packages/env` validates `process.env` at import time and throws a field-by-field error if anything is missing — including in dev. There is no reduced "dev mode" schema. Note what's genuinely NOT in `.env` anymore: Microsoft Entra ID, AI provider, and mail vendor config all live in the `system_settings` DB table, set through the app itself (`/setup` on first boot, `/settings` after that) — see below.

`pnpm build` / `pnpm typecheck` / `pnpm test` run across the whole workspace via Turborepo.

## First run: /setup

Every route redirects to `/setup` until Microsoft Entra ID is configured (`apps/web/src/routes/__root.tsx`'s `beforeLoad` checks `system_settings` on every navigation). This is deliberate — a SaaS-style deploy shouldn't need `.env` edits for business config, just infra secrets, then a form:

1. Deploy with a filled-in `.env` (infra-level only, see `.env.example`) and run migrations.
2. Open the app in a browser. You land on `/setup`.
3. Enter the Entra ID app's **Tenant ID** (a concrete GUID — not `common`/`organizations`/`consumers`), **Client ID**, and **Client Secret**. Register this redirect URI on the Azure app first: `https://<your-domain>/api/auth/callback/microsoft-entra-id`.
4. Submitting writes encrypted credentials to `system_settings` and invalidates the in-memory Better Auth instance (`apps/web/src/lib/auth.ts`'s `getAuth()`/`invalidateAuthCache()`) — the very next request rebuilds it with Microsoft sign-in enabled. **No restart needed.**
5. `/setup` now permanently redirects to `/login` — it only ever runs once. Re-editing Entra credentials later is a separate, admin-gated path: a Microsoft Entra ID section on `/settings`, calling the same `completeSetup()` again (blank Client Secret keeps the existing one, same "leave blank to keep" convention as the AI/mail sections) and invalidating the auth cache exactly like the original `/setup` flow. The form shows an explicit warning about the operational gotcha below — this doesn't fix that fragility, just makes an admin editing this aware of it before they save.
6. **The first person to complete Microsoft sign-in becomes the owner of a brand-new, auto-created workspace.** Everyone after that is a plain user with no workspace until an existing admin invites them.

**Inviting members** — an admin-only `/members` page (member list, pending invitations, an invite-by-email form) plus a public `/invite/{invitationId}` accept page. This wires up Better Auth's own `organization` plugin invitation API (`createInvitation`/`acceptInvitation`/`rejectInvitation`/`cancelInvitation`/`listInvitations`) rather than building anything custom — the plugin already had a full `invitation` table and endpoints, just never configured with a `sendInvitationEmail` callback (Better Auth deliberately doesn't build the accept URL or send the email itself). The invitee must already be signed in for `acceptInvitation` to succeed (it checks the accepting session's email against the invitation's) — there's no first-time-signup handling, so the accept page shows a "sign in with Microsoft" prompt first when there's no session, returning to the same accept URL afterward. **Not interactively verified end-to-end** — same limitation as the AI UI (P7) and JIRA's live success path (P8): no real Entra ID tenant in this environment to complete a real login against, and deliberately not worked around by faking a tenant ID (that triggers the OIDC-discovery-on-boot fragility documented just below and takes down the whole container). The `sendInvitationEmail` logic itself (the one piece of this actually written for Kompast, not Better Auth's own already-tested code) is covered by a real-Postgres test.

Group-claim → workspace-role mapping (`entra_group_map` table) has no admin UI yet.

**⚠️ Operational gotcha, confirmed by hand (twice — before and after moving Entra config into the DB):** `microsoftEntraId()` always performs live OIDC discovery against `https://login.microsoftonline.com/<tenant>/v2.0/.well-known/openid-configuration` to fetch the JWKS needed for ID-token verification, and its options type has no way to skip or override that. If the tenant is wrong, or Microsoft's discovery endpoint is briefly unreachable, Better Auth's plugin init throws — and because every plugin shares one auth context, **this takes down the entire app, not just Microsoft sign-in**: every route that calls `auth.api.getSession()` (which is every authenticated page) 500s. Since `/setup` only runs once, a wrong tenant entered there currently has no UI path to fix — you'd need to correct `system_settings.microsoft_tenant_id` directly in Postgres (then hit any route once to force `getAuth()` to rebuild — it re-reads settings on every call and only reuses the cache when the read matches what's cached). Fixing the underlying fragility would mean setting `requireIdTokenVerification: false` on the provider, trading away ID-token signature verification for availability — a security tradeoff intentionally left alone here, not made unilaterally.

## Settings: AI + mail (`/settings`, admin-only)

Once at least one workspace exists, its owner/admin can sign in and open `/settings` (linked from the sidebar, hidden for non-admins) to configure:
- **AI provider** — Anthropic, Azure OpenAI, or an OpenAI-compatible endpoint, plus a per-workspace feature toggle. No AI *features* consume this yet (that's P7) — this is the storage + admin UI landing ahead of it, since the whole point of this pivot is that these are never `.env` vars.
- **Mail vendor** — Brevo, Resend, or raw SMTP. Same story: `packages/mail` doesn't exist yet (P5), this just gives it somewhere to read config from once it does.

Both are stored in `system_settings` with secrets encrypted via `packages/core/src/crypto.ts` (AES-256-GCM, keyed from `BETTER_AUTH_SECRET`) — never in plaintext, and the settings API never echoes a stored key back to the client, only a `hasApiKey: boolean`. Leaving the API-key field blank when saving keeps whatever's already stored; it does not clear it.

## Docs (P2)

Real-time collaborative pages, workspace-level or filed under a project (the "Docs" tab on any project page). `/docs` in the sidebar for the workspace-level tree.

- **Editor** — BlockNote (`apps/web/src/components/docs/Editor.tsx`), synced live via `apps/collab`'s Hocuspocus server. `apps/collab` authenticates each WebSocket connection with a short-lived HMAC-signed token minted per page-load (`packages/core/src/collab-token.ts`) after a normal page-access check — it has no workspace session of its own, so this is the only way it can verify "this user may edit this page" at all.
- **Permissions** — a page with no explicit grants is open to any org member (same default P1 already gives boards/projects). Adding a `page_permission` row for specific users/teams makes it restricted to just those subjects.
- **Version history** — `apps/collab` snapshots into `page_version` roughly every 5 minutes while a page is being edited (in-memory interval, per-process — revisit if the collab tier is ever more than one instance). Restoring a version decodes it server-side to BlockNote blocks and applies them through the *live* editor (`editor.replaceBlocks`), never by overwriting stored Yjs state directly — the latter would race with anyone else currently connected.
- **kompastView embed** — `/tabel` in the editor inserts a live, read-only rendering of a board's table view, permission-checked against the *current reader's own session* on every load, never trusted from the block's stored props.
- **@mentions** — `@` in the editor links to another page; the mention's title/icon are captured at insert time (won't retroactively update if the target is renamed) and feed the backlinks panel via the same `link` table used for explicit doc↔issue links.
- **Templates** — mark any page as a template from its own toolbar; `/docs` lists them with a "Gunakan" action that duplicates the template's content into a new page.
- **Trash** — archiving cascades to a page's descendants; `/docs/trash` lists everything archived, with restore or permanent (irreversible) delete.
- **Guest share links** — `/s/:token`, no session, no workspace context at all. The token is the entire credential, verified in `packages/core/src/share-link.ts` against the admin DB connection (the one deliberate exception to every other query going through `withAuthorizedTenant`). Content is rendered server-side from the stored Yjs bytes via `@blocknote/server-util`, and a `kompastView` embed is always replaced with a placeholder before that export — BlockNote attaches every block's props as raw `data-*` HTML attributes regardless of its own render function, so the only reliable way to keep an embed's board/view IDs out of guest-facing HTML is to never hand that block to the exporter at all.

**Gotcha, hit and fixed by hand:** `@blocknote/react`/`@blocknote/core`/`@blocknote/shadcn`/`@blocknote/server-util`/`@hocuspocus/*` all peer-depend on `yjs`/`y-protocols`/`y-prosemirror`, and pnpm resolved *three different instances* of `@blocknote/core` across the workspace based on differing `y-protocols` versions pulled in transitively. TypeScript correctly flagged this ("separate declarations of a private property"); the root package.json pins `y-protocols` via `pnpm.overrides` to collapse most of it, but a couple of call sites in `apps/web/src/components/docs/Editor.tsx` still need a narrow, commented `as any` where TS can't see through the dual-instance history. Not a runtime bug — verified by the real Yjs encode/decode round-trip tests in `apps/web/src/lib/__tests__/blocknote-schema.test.ts` and `apps/collab/src/__tests__/server.test.ts`.

## REST API + MCP (P3)

Every mutation lives exactly once in `packages/core`, behind the same permission check and `withAuthorizedTenant` transaction, regardless of whether it's called from the UI, `/api/v1`, or `/mcp` — that's the whole point of the architecture, so REST and MCP can't drift apart in what they allow.

- **Personal access tokens** — generate one at `/tokens` (Better Auth's `apiKey` plugin, `kmp_…` prefix, scoped to `issues:read/write`, `pages:read/write`, `admin`, optional expiry, revocable). A token can never exceed the granting user's own workspace permissions.
- **REST** — `/api/v1/issues`, `/api/v1/pages`, `/api/v1/search`, all `Authorization: Bearer kmp_…`, RFC 9457 `problem+json` errors, `Idempotency-Key` header on creates. `pages` PATCH is deliberately metadata-only (title/icon) — overwriting a page's Yjs document from outside its collab session would race with anyone live-editing it; content is only settable on create. See `/api/docs` (Scalar, generated from `apps/web/src/lib/openapi-spec.ts`) for the full endpoint list.
- **MCP** — `/mcp`, Streamable HTTP, stateless (a fresh server is built per request, scoped to that request's authenticated token — no session, so it needs no session affinity behind a reverse proxy). PAT-only auth, same bearer token as REST:
  ```bash
  claude mcp add --transport http kompast https://<domain>/mcp \
    --header "Authorization: Bearer kmp_…"
  ```
  Tools mirror the REST surface 1:1 (`create_issue`, `transition_issue`, `comment_page`, `link_page_to_issue`, etc. — see `apps/web/src/lib/mcp-server.ts`), plus `kompast://issue/{key}` / `kompast://page/{id}` resources and `bug-report` / `pr-to-issue` / `standup-digest` prompts. A missing token scope comes back as a tool-level error, not an HTTP 403 — one `/mcp` POST is one JSON-RPC call, so there's no earlier point to reject a specific tool's scope requirement.
- **Attribution** — every REST/MCP write sets `origin`/`originClient` on the issue/page/comment (`"api"`/`"mcp"` + the request's `User-Agent`), so the activity feed reads "via Claude Code", not silently as the user's own UI action.

**Gotcha, hit and fixed by hand:** `@blocknote/server-util` (used to render page content as Markdown for REST/MCP) depends on `jsdom`, which cannot be bundled into Nitro's otherwise-self-contained SSR output — one of its internal CJS modules reads its own default stylesheet via a `__dirname`-relative path, and every request 500'd once that got relocated into a bundled chunk. Found via a real `docker build` + `docker run`, not just `pnpm build` (dev server and `vitest` never touch the built Nitro output, so this class of bug is invisible to either). Fixed by declaring `jsdom` as a direct `apps/web` dependency (pnpm's isolation otherwise hides it as a phantom transitive dep), marking it external in `vite.config.ts`'s `nitro.rollupConfig`, and having `infra/Dockerfile.web` run `pnpm deploy --prod --legacy` so the runtime image gets a real, non-symlinked `node_modules` for it instead of only the bundled `.output`.

## Sprints, roadmap (P4)

- **Sprint lifecycle** — `packages/core/src/sprint.ts`. Create a sprint (`1w`/`2w`/`3w`/`4w`/`custom` cycle), add/remove issues to/from it (backlog ↔ sprint), start it (enforces one active sprint per board; marks whatever's attached at that moment `plannedAtStart`), complete it (whatever isn't in a "done"-category status carries to another sprint or back to the backlog; velocity = completed points). `sprint_issue` is membership *history*, not just current state, so scope added mid-sprint is distinguishable from what was originally planned.
- **Reports** — `packages/core/src/sprint-report.ts` reconstructs a day-by-day series from `sprint_issue` + `issue_history` (there's still no nightly snapshot cron for this specifically — `apps/worker`'s queue infra, added in P5, isn't wired to sprint snapshots) for burndown and cumulative flow; velocity history reads the `sprint_snapshot` rows taken at each sprint's start/complete. `GET /api/v1/sprints/{id}/report`, `GET /api/v1/velocity?projectKey=`.
- **Epics + roadmap** — an epic is just an issue whose type has `hierarchyLevel = 0` (not matched by the name "Epic", since nothing stops that row from being renamed). `updateIssue`/REST PATCH/`update_issue` (MCP) all take an `epicKey` to link a child issue to one. `GET /api/v1/roadmap?projectKey=` / `get_roadmap` (MCP) list each epic's date range and child completion. The project page's Roadmap tab renders this as a simple progress bar per epic — not a drag-resizable Gantt.
- **UI** — a "Sprint" tab on the project page: sprint picker/create, a live scope/completion summary, backlog and current-sprint-issues panes with add/remove buttons (no drag-and-drop between them yet, unlike the kanban board), and a "Tinjauan sprint" (sprint review) table below them — the board's own `TableView` component reused verbatim (`SprintReviewTable` in `$projectKey.tsx`), just filtered to the sprint's current issue set, with the same group-by/sort-by controls and one shared project-level saved-view config (not a separate one per sprint — a deliberate simplification). Cells are still read-only (linking out to the issue detail page to edit) — full inline-cell editing is a separate, larger gap across the whole table view feature, not unique to sprint review.
- **REST/MCP** — `sprints:write` token scope gates all sprint mutations (create/start/complete/add/remove-issue). MCP: `list_sprints`, `get_sprint`, `start_sprint`, `complete_sprint`, `get_roadmap` — the first two P3 explicitly deferred here.
- **Not built this pass**: inline-cell editing anywhere in the table view (status/assignee/etc. changes still require opening the issue).

## Notifications & mail (P5)

- **`notify()`** (`packages/core/src/notification.ts`) is the single call site for "something happened, tell this user" — reads the user's per-workspace, per-event preference (`notification_pref`; defaults to in-app + instant email if the user never touched it) and writes an in-app `notification` row and/or enqueues an email accordingly. Wired into two real triggers so far: assigning an issue to someone (never for self-assignment) and commenting on one (notifies the assignee + reporter, never the commenter about their own comment). `NOTIFICATION_EVENT_TYPES` is the fixed registry the preferences UI renders — add to it whenever a new `notify()` call site is added elsewhere.
- **Email delivery** — `enqueueEmail()` writes an `email_outbox` row in the same transaction as whatever triggered it (a transactional outbox, not a direct send — an email is never promised for a mutation that then rolls back). `apps/worker` runs a real BullMQ `Worker` on a `mail` queue that claims pending rows (`FOR UPDATE SKIP LOCKED`, admin connection — a system-wide scan across every workspace, not one tenant's request) and sends them via `packages/mail`. There's no explicit "wake up now" signal from `apps/web` yet — a repeatable job polls every 15s, so worst-case delivery latency is that interval (fine for notification email, not for anything latency-sensitive).
- **`packages/mail`** — driver interface (Brevo, Resend, SMTP via nodemailer) chosen by `getMailCredentials()`'s decrypted config (the runtime counterpart to `/settings`'s masked `getMailSettings()` view), with one React Email template (`NotificationEmail`) rendered to HTML + a plain-text fallback before handoff to the driver.
- **UI** — a notification bell in the topbar (30s poll, unread count, mark-as-read) and a personal `/notifications` page for per-event in-app/email/digest preferences (distinct from the admin-only `/settings`, which only holds the workspace-wide mail driver config).
- **Not built this pass**: hourly/daily digest batching (choosing a non-instant digest cadence today just stops the instant email, without anything replacing it yet), bounce/complaint webhook handling → suppression list, and outbound webhooks.

**Gotcha, hit and fixed by hand:** `apps/worker`'s build had to switch from ESM to CJS output after two real bundling bugs, found one at a time via an actual `node dist/...` run (not assumed): `ioredis` (and its own `node-abort-controller` dependency) do computed/deep-subpath `require(...)` calls esbuild can't turn into ESM imports ("Dynamic require of ... is not supported"), and even once excluded from the bundle, Node's own ESM loader refuses to resolve their extensionless deep imports (`ERR_UNSUPPORTED_DIR_IMPORT`) — a strictness plain CJS `require()` doesn't have. CJS sidesteps both.

## Automation (P6)

- **Event model** — every mutation that should be able to trigger a rule (`createIssue`, `updateIssue`, `moveIssue`, `addComment`) writes an `automation_event` row (`issue.created`/`issue.updated`/`issue.transitioned`/`issue.assigned`/`issue.commented`) in the same transaction as the domain change — a transactional outbox, same pattern as P5's `email_outbox`. `apps/worker` runs a second BullMQ queue (`automation`, polled every 5s, independent of the `mail` queue's 15s) that claims pending events (`FOR UPDATE SKIP LOCKED`, admin connection) and hands each to the engine (`packages/core/src/automation.ts`).
- **Rules** — `automation_rule` (project-scoped, jsonb `trigger`/`conditions`/`actions`, `enabled`, `dryRun`). Conditions compare a resolved field (`eq`/`neq`/`in`/`contains`) against a value — this already covers "assignee in team X" today if the caller resolves team membership to a user-id list first via `{field: "assigneeId", operator: "in", value: [...]}`, but nothing does that resolution yet, so it's reachable only by hand-building the condition, not through the UI. Actions are `transition`/`assign`/`set_field`/`add_label`/`comment`/`notify`/`add_to_sprint`/`link_issue`/`create_subtask` (fixed title, not templated from the triggering issue; defaults to the project's first todo-category status, same fallback `apps/web`'s own resolvers use). The engine works purely on IDs (status/assignee/sprint), never names — resolving a human-typed name to an ID is left to whichever caller already has that lookup done (REST/MCP callers, and this project page's own rule-builder UI).
- **Guardrails** — max chain depth 5 (an event at/past that depth is skipped with no run logged at all); a rule never re-fires on the event its own action just caused (`causedByRuleId`), though *other* rules still see and can react to that event; a per-rule rate limit (50 matched runs/hour); dry-run mode (logs `status: "dry_run"` without applying the action); every candidate rule evaluated against every event gets an `automation_run` row — including `not_matched` and `skipped_rate_limited` — not just the ones that fired.
- **Attribution** — an automation-driven mutation is written with `actorId: rule.createdBy`, `origin: "automation"`, `originClient: automation:<rule name>`, so the activity feed and `issue_history` can tell "a person did this" from "a rule did this" — the same attribution discipline P3 established for MCP writes.
- **REST/MCP** — `POST/GET /api/v1/automation/rules`, `GET/PATCH/DELETE /api/v1/automation/rules/{id}`, `GET /api/v1/automation/rules/{id}/runs`, all gated by `issues:write`/`issues:read` (no separate automation scope — a rule is just another way project data gets mutated). Not exposed as MCP tools this pass — REST only.
- **UI** — an "Otomasi" tab on the project page: create a rule (name + trigger dropdown + **one** action), enable/disable, expand a rule's run history, delete. No condition-builder UI (conditions are REST/API-only for now), and the UI can only build a single-action rule per rule (the engine and schema support an array of actions; the form doesn't yet).
- **Not built this pass**: `run_ai_prompt`/outbound-webhook action types (schema has room for them, engine doesn't implement them), a team-membership-to-user-ids resolver (what would make "assignee in team X" conditions actually reachable from a UI), and a condition-builder or multi-action UI.
- **Verified**: a real `docker build`+`docker run` of both `kompast-web` and `kompast-worker` images against the dev Postgres/Redis — created a rule and an issue over the live REST API, transitioned the issue, and confirmed the containerized worker's automation queue picked up the resulting `issue.transitioned` event within one poll interval, applied the `add_label` action, and logged a `matched` run visible through `GET .../runs` — end to end, no mocking.

## AI assist (P7)

- **Provider adapter (`packages/ai`)** — one `AiDriver` interface (`streamCompletion({messages, maxTokens}, onDelta) → {text, inputTokens, outputTokens}`), three drivers, all raw `fetch` against each provider's own streaming endpoint (no `@anthropic-ai/sdk`/`openai` SDK dependency, mirroring `packages/mail`'s driver pattern): Anthropic (`/v1/messages`, SSE), Azure OpenAI (`{endpoint}/openai/deployments/{deployment}/chat/completions`), OpenAI-compatible (`{baseUrl}/chat/completions` + Bearer — for a self-hosted/local model server). Azure and OpenAI-compatible share one SSE-parsing implementation (`drivers/openai-chat.ts`) since they speak the same Chat Completions wire format. Config comes from `/settings`'s existing AI section (built in P0, unused until now) — this pass added the missing `model` field there (`system_settings.ai_model`), since Anthropic/OpenAI-compatible need a model name that Azure's deployment-name field already implicitly provided.
- **Governance (`ai_usage`)** — `packages/core/src/ai.ts`'s `runAiCompletion()` is the single call site every AI feature funnels through: it resolves `getAiCredentials()` (null means "off," whether that's because nothing was ever configured or an admin explicitly disabled it — treated identically), builds a client, streams the completion, and logs one `ai_usage` row per call (`feature`, `provider`, `model`, `inputTokens`, `outputTokens`). No cost/$ column — provider pricing changes independently of this table, and a hardcoded price would silently go stale; token counts are the durable fact, cost is left as a report built later against current pricing. No monthly-token-budget *enforcement* either, despite the plan calling for it — `ai_usage` has what a budget check would need (org + timestamp + tokens), but nothing reads it back to block a call yet.
- **Three real features, one pattern each**: a `packages/core` function builds a feature-specific prompt, calls `runAiCompletion`, and is exposed through one session-cookie-gated SSE route (`POST /api/ai/stream`, `apps/web/src/routes/api/ai.stream.tsx` — UI-only, deliberately not a `/api/v1` or MCP surface this pass, see below).
  - **Doc writing assist** — continue / improve / shorten / expand / summarize / translate (ID↔EN, as two fixed language options rather than a language picker). Wired into the doc editor's `/` slash menu (group "AI") in `apps/web/src/components/docs/Editor.tsx`: an action reads the current block's Markdown (or, for "continue," everything before it) via BlockNote's own `blocksToMarkdownLossy`, inserts a "AI sedang menulis…" placeholder block, streams the completion, then replaces the placeholder with the result parsed back into blocks (`tryParseMarkdownToBlocks`). **Always inserts as a new block after the current one — never an in-place rewrite of the original text**, even for "improve"/"shorten"/"expand" where in-place would arguably read better; a deliberate simplification so every action shares one code path instead of a second one this environment couldn't interactively verify (no Entra ID login available here — see Verified, below).
  - **Issue description draft** (`generateIssueDescription`) — title (+ optional free-text context) → a Markdown description with acceptance criteria, for the user to review before saving. The issue detail page now has a description section (view/edit toggle, plain textarea, `{text: string}` shape — not a full BlockNote document) with a "Buat draft dengan AI" button that streams a draft into the textarea for review, never auto-saving — a later pass closed the P1/P2 gap this feature originally shipped without (the page had no description UI at all).
  - **Sprint summary** (`generateSprintSummary`) — a short retro-style paragraph from the same data the Sprint tab's report already shows (scope/completed/remaining points, completed vs. not-completed issue titles), narrated in prose rather than re-listing every issue. A "Buat ringkasan" button on the Sprint tab streams it in below the existing report stats.
- **Not built this pass**: epic→subtasks breakdown, duplicate-issue detection, assignee/story-point suggestion, template generation, release notes from a version, standup digest, risk flags, autofill table column, a refreshable "/ai summary" block, monthly token budget enforcement, and any REST/MCP-exposed AI tool (AI is UI-only this pass — `/api/ai/stream` is session-cookie auth, not a PAT/scope surface).
- **Verified**: `pnpm typecheck && pnpm build && pnpm test` green across all 10 packages (added `packages/ai`, 20 tests, all against a mocked `fetch` — no real provider call, no API cost — covering every driver's request shape, SSE parsing including a frame split across two chunk reads, and config-validation errors per provider); `packages/core`'s `runAiCompletion`/`runDocTextAction`/`generateIssueDescription`/`generateSprintSummary` covered end-to-end against a real Postgres with a mocked Anthropic SSE response (token counts, prompt contents, and `ai_usage` logging all asserted); a real `docker build`+`docker run` of `kompast-web` confirmed `/api/ai/stream` 405s on GET and 401s an unauthenticated POST in the actual containerized server. **What's genuinely not verified**: the interactive browser flows (the slash-menu items, the Sprint tab's button) against a real LLM call — this sandbox has neither a real Entra ID tenant to log in with nor a live provider API key to call, and spending one to self-verify wasn't the right call to make unilaterally. Treat the doc-editor and sprint-summary UI as needing a human smoke test before relying on them in production.

## Ask Kompast — RAG chat (P7 stage A: issues + comments; docs are stage B)

A workspace knowledge-base chat: semantic search (pgvector) over issue titles/descriptions and comments, feeding a retrieval-augmented answer from the workspace's existing chat AI provider. Deliberately built in two stages, verified independently — see "Not built this pass" below for why docs/pages indexing is stage B, not skipped.

- **Infra** — switched the Postgres image from vanilla `postgres:17-alpine` to `pgvector/pgvector:pg17` (`infra/docker-compose.yml`, CI's service container, and the local dev container) — a drop-in-compatible image with the pgvector extension precompiled. `packages/db/src/migrate.ts` runs `CREATE EXTENSION IF NOT EXISTS vector` before migrations, since the `embedding` table's `vector(1536)` column needs the type to exist first. 1536 dimensions is fixed at the column level (pgvector requires a fixed size, matching OpenAI/Azure's `text-embedding-3-small`) — switching to a different-dimension model later means a migration plus a full reindex, not a settings change.
- **A separate embedding provider, not a reuse of the chat AI provider** — Anthropic (a valid *chat* provider choice) has no public embeddings API at all, so `/settings` has an independent "Embedding (Ask Kompast)" section (Azure OpenAI or OpenAI-compatible only) with its own credentials/model/endpoint, gated by its own `embeddingFeaturesEnabled` toggle. `packages/ai` gained `createEmbeddingClient()`/`EmbeddingDriver` alongside the existing chat `AiDriver` — same raw-`fetch`, no-SDK shape, sharing the OpenAI-Embeddings-response parsing between the Azure and OpenAI-compatible drivers the same way the chat drivers already share the Chat-Completions parsing.
- **Indexing** — `packages/core/src/rag.ts`'s `indexEntity()` chunks text (paragraph-aware, ~1000 chars/chunk, no sentence-level splitting) and embeds each chunk, replacing any existing chunks for that entity wholesale (never merged/diffed — simplest correct behavior whether content shrinks or grows). Reindexing is a transactional outbox, same pattern as `email_outbox`/`automation_event`: `createIssue`/`updateIssue`(title or description changed)/`addComment` enqueue a row in the *same* transaction as the mutation — including for `origin: "import"` (a bulk-imported issue should be just as findable as a live-created one, unlike notifications/automation, which imports deliberately never fire) — and `apps/worker` runs a third BullMQ queue (`reindex`, polled every 10s) that claims pending rows and re-reads the entity's *current* content fresh at process time, never from a stale queue payload.
  - **Sprint context, folded in, not live** — an indexed issue's text includes its sprint's name/goal at the time it was last (re)indexed (so "what were we shipping in the Q3 auth sprint" can surface issues via their own embeddings). Moving an issue between sprints does **not** itself trigger a reindex — wiring that into `addIssueToSprint`/`removeIssueFromSprint` would create a real circular import (`sprint.ts → rag.ts → ai.ts → sprint.ts`, since `ai.ts`'s `generateSprintSummary` already imports from `sprint.ts`) for a freshness improvement judged not worth that risk. The sprint context goes stale until the issue's title/description is next edited.
- **Retrieval + generation** — `askKompast()` embeds the question, vector-searches `embedding` (cosine distance, org-scoped — issues/comments have no extra per-row permission layer the way pages will in stage B, so no additional filtering needed yet), folds the top matches into a system prompt alongside the thread's prior messages, and calls the *chat* provider via the same `runAiCompletion()` every other AI feature uses. Both the question and the answer (with citations: which chunks fed it) are persisted as `ai_message` rows under an `ai_thread`; a new thread's title is auto-derived from the first question.
- **UI** — a new "Tanya Kompast" sidebar link (`/ask`): a thread list + streaming chat, backed by a session-cookie-gated SSE route (`POST /api/ask/stream`, same UI-only shape as `/api/ai/stream` — no REST/MCP surface this pass either).
- **No live tool-calling for numeric sprint state** — a deliberate scope decision, decided with the user up front: burndown/velocity/"what's blocking sprint X right now" are structured, current-state data that goes stale immediately if embedded and doesn't benefit from semantic similarity search. The right architecture is a tool-call the assistant can invoke on demand (reusing P4's `getSprintReport`/`getBurndown`), not more embedding — not built this pass; `packages/ai`'s `AiDriver` doesn't support function/tool-calling at all yet, which would be its own real addition (each provider has a different tool-call JSON shape and a multi-turn tool-result exchange).
- **Not built this pass**: docs/pages indexing (stage B) — page content lives as Yjs binary state, and converting it to plain text needs `@blocknote/server-util`, which depends on `jsdom`, the exact library that broke `apps/web`'s Nitro ESM bundling in P3. Adding it to `apps/worker` (also a bundled build) carries real, unverified risk of the same class of bug — deliberately sequenced as a separate, independently-Docker-verified step rather than risking two unknowns (does the core RAG pipeline work at all, does jsdom bundle cleanly in a second service) at once. Also not built: permission-filtered retrieval (needed once pages — which *do* have per-page restrictions via `page_permission` — are indexed; issues/comments don't need it), a full-reindex-everything admin action, and any REST/MCP surface for Ask Kompast.
- **Verified**: real-Postgres tests (co-located in `settings.test.ts` — `system_settings` is a true singleton and this describe block also writes to it, same cross-file-race reasoning as the existing "packages/core/ai" tests there) cover chunking, wholesale chunk replacement, the full enqueue→claim→process pipeline via a real `createIssue`/`addComment` call, similarity-ordered search (a deterministic hash-based fake embedding function stands in for a real model — no real semantic behavior to test against a mocked provider, but the retrieval *mechanics* — store, order by distance, retrieve — are exercised for real), and `askKompast`'s end-to-end behavior (retrieval, generation, persistence, citations, thread continuation, the not-configured error). Found and fixed one real bug while writing these: the reindex queue is claimed system-wide (every test file's own `createIssue`/`addComment` calls enqueue onto the *same* queue), so asserting against `claimPendingReindexTasks(...)[0]` raced other concurrently-running test files — fixed the same way `claimPendingAutomationEvents`'s own test already had to (filter the claimed batch by a known id, don't assume position). A real `docker build`+`docker run` of both `kompast-web` and `kompast-worker` confirmed `/api/ask/stream` 405s on GET and 401s an unauthenticated POST, and — since no real embedding provider credentials exist in this environment — a real issue created against a deliberately-unreachable embedding endpoint produced a genuine DNS failure that the containerized worker's reindex queue caught and recorded correctly (same "prove the real failure path since the real success path needs credentials this environment doesn't have" approach as P8's JIRA importer verification).

## Attachments / storage

`packages/storage` has two drivers behind one interface (`getUploadUrl`/`getDownloadUrl`/`delete`), chosen by `STORAGE_DRIVER`:
- **`local`** (default, dev/CI only) — the browser PUTs/GETs through `apps/web`'s own `/api/storage/{upload,download}/*` routes, gated by an HMAC-signed, short-lived token (`packages/storage/src/local.ts`) rather than real cloud signed URLs. Files land on one container's local disk (`STORAGE_LOCAL_DIR`) — this does not survive a redeploy and does not work if you ever run more than one `web` instance.
- **`gcs`** (production) — real V4 signed URLs; the browser uploads straight to Google Cloud Storage, never through the Node process. Set `STORAGE_DRIVER=gcs` and the GCS variables below.

In both cases, the Node process never touches file bytes — it only ever issues a signed URL after checking the requester's permission via `withAuthorizedTenant`, in `packages/core/src/attachment.ts`.

## GCP storage setup

1. Enable the Cloud Storage API on your GCP project.
2. Create a private bucket (uniform access, no public bindings), regional close to your Debian host.
3. Create a service account with `roles/storage.objectAdmin` scoped to *that bucket* (bucket-level IAM binding), not project-wide.
4. Download its JSON key to the Debian host, outside the git-ignored build context — e.g. `/etc/kompast/gcs-service-account.json`, `chmod 600`.
5. `docker-compose.yml` mounts it read-only at `/run/secrets/gcs.json`; set `GOOGLE_APPLICATION_CREDENTIALS=/run/secrets/gcs.json`, `GCS_BUCKET`, `GCS_PROJECT_ID` in `.env`.
6. Apply CORS so direct browser→GCS signed uploads work:
   ```bash
   gcloud storage buckets update gs://<bucket> --cors-file=infra/gcs-cors.json
   ```
   Edit the `origin` field in that file to your real domain first.

Object storage code itself (`packages/storage`) lands in P0's remaining work / P1 attachments — the env vars and bucket are worth provisioning now so nothing blocks on IT turnaround later.

## Importers (P8, JIRA only so far)

- **`packages/import`** — extract → map → load, one source folder per importer (`src/jira/`). `fetchJiraIssues()` pages JIRA Cloud's real `GET /rest/api/3/search` (`email:apiToken` Basic auth, `expand=changelog`, `fields=*all`) until `total` is exhausted; `parseJiraExportFile()` reads the same shape from a checked-out JSON export as a fallback with no live API call. `mapJiraStatusCategory()` trusts JIRA's own `statusCategory.key` directly (`new`/`indeterminate`/`done` → `todo`/`in_progress`/`done`) — there's no separate human-confirms-the-mapping UI step this pass, despite the plan calling for one; `runJiraImport()`'s dry-run report (`statusMapping`/`typeMapping`) is the only review surface today.
- **What a run does**: creates any JIRA status/type the target project doesn't already have (matched case-insensitively by name); creates every issue not already linked via `external_ref` (idempotency key: `(organizationId, "jira", jiraIssueKey)`); backfills parent linkage in a second pass (since a subtask can appear before its parent in JIRA's result ordering); on issues newly created *this run only* — comments, worklogs, issue links (outward side only, to avoid double-loading JIRA's own bidirectional link reporting), attachments (only if a `downloadAttachment` callback is supplied — otherwise counted as `attachmentsSkipped`, never silently dropped), and changelog-derived historical status transitions (`recordHistoricalStatusChange` — a backdated `issue_history` row only, deliberately not `moveIssue`, which would also mutate the issue's *current* status). Every issue is wrapped in its own try/catch — one bad issue's error lands in the report, not a killed run.
- **`fixVersions`/`components`** land in `issue.customFields.jira` rather than first-class `version`/`component` rows — folded in deliberately, not a placeholder; giving JIRA versions/components their own management surface is a separate feature from importing one, and isn't scheduled.
- **ADF → text**: `adfToPlainText()` is a best-effort plain-text walk of JIRA Cloud's Atlassian Document Format tree (used for descriptions/comments) — joins text leaves, blank-lines between block nodes, drops all formatting (bold/links/tables/panels) rather than reconstructing it. Lossy on purpose: it never throws on an unrecognized node shape, unlike a strict renderer would.
- **Bulk-import semantics**: every write goes through `createIssue`/`updateIssue`/`addComment` with `origin: "import"`, which suppresses notifications and automation entirely (importing 5,000 historical issues must not send 5,000 assignment emails or fire live-workflow rules) — the one exception is `createWorkflowStatus`/`createIssueType`/`logWork`/`linkIssues`/`attachIssueFile`, which have no notify/automation side effect to suppress in the first place.
- **Trigger surface** — `POST /api/v1/imports` (`{source:"jira", projectKey, jiraBaseUrl, jiraEmail, jiraApiToken, jql, dryRun?, fetchAttachments?}`, `issues:write`) starts a run; `GET /api/v1/imports?projectKey=` / `GET /api/v1/imports/{id}` (`issues:read`) list/inspect one. An "Impor" tab on the project page is the same thing for a human: a form + a history list, via a session-gated server function (`startJiraImportFn`) rather than the REST route itself. **Runs synchronously in the request** — no background job/queue for imports exists; a very large JIRA project may exceed a typical reverse-proxy timeout, a known limitation rather than something this pass builds around. The JIRA network fetch deliberately happens *between* two short `withAuthorizedTenant` transactions (create+mark-running, then resolve-users+load+complete), not inside one held open across a potentially slow paginated fetch. The JIRA API token is passed at call time only (matching `createImportRun`'s already-non-secret-only `config` field) and, in the UI, cleared from component state right after one submit.
- **Email→Kompast-user resolution** — `collectJiraEmails()` gathers every distinct reporter/assignee/comment-author/worklog-author email across the fetched batch; the REST/server-fn layer resolves each once against `member`/`user` (a DB query `runJiraImport`'s own synchronous `resolveUserId` callback can't make itself) before the load pass runs. An email with no matching Kompast member just leaves that field unset — there's no directory sync.
- **Verified**: a golden-fixture test (`packages/import/src/__tests__/jira.test.ts`, a 3-issue fixture with a parent/subtask pair, a cross-issue block link, a comment, a worklog entry, and one changelog status transition) against a real Postgres — dry-run writes nothing; a real run creates all 3 issues, resolves the parent link, and gets every count right; running the same import twice creates zero new issues/statuses/types and does not duplicate the comment. REST tests mock JIRA's search response (no real network call, no real credentials needed) for the create/dry-run/list/detail/scope-rejection paths. A real `docker build`+`docker run` of `kompast-web` additionally confirmed the whole create→run→fail→readable-via-GET lifecycle against a genuinely unreachable host (no mocking) — since no real JIRA account exists in this environment to test the success path against a live server, that's the one thing still resting on the mocked-fetch tests alone.
- **Not built at all**: the Notion importer (extractor, the 30+-block-type→BlockNote converter, second-pass internal-link rewrite, incremental-sync worker job) — none of it exists yet, this pass is JIRA-only. Also not built: any background job/queue for a long-running import (synchronous REST only, see above), a human-confirms-the-status-mapping UI step before a real run applies it, attachment streaming has no live JIRA-auth test (the `downloadAttachment` callback is wired into both REST and the UI form's "Unduh lampiran" checkbox, but never exercised against a real JIRA attachment URL), and the post-import reconciliation report the plan calls for is today just `JiraLoadReport`'s counts rendered as a compact summary — not the fuller "counts in vs counts out, unresolved links, skipped blocks" report the plan describes.
- **Credentials needed ahead of a real run**: JIRA Cloud — `email` + API token, `https://<site>.atlassian.net`. Notion — an internal integration token (Settings → Connections in Notion, shared on the target pages), not used yet since the Notion importer doesn't exist.

## Deploying

```bash
cd infra
cp .env.example .env   # fill in every value
docker compose pull
docker compose up -d
```

- Every service binds to `127.0.0.1` only — Caddy fronts them. See `infra/Caddyfile.example`; the important bit is that `/api/collab/*` must route to the `collab` service **before** the catch-all `reverse_proxy` to `web`, or the Yjs WebSocket upgrade 404s.
- `migrate` is a one-shot service (`infra/Dockerfile.migrate`) that `web` waits on (`depends_on: service_completed_successfully`) — it runs `packages/db`'s Drizzle migrations directly against `DATABASE_URL`.
- Images are built and pushed to GHCR by `.github/workflows/release.yml` on every push to `main` (tag `latest`) and on `v*` tags (semver tag). Set `GHCR_OWNER` in `.env` to your GitHub org/user.
- The `migrate` step runs three things in order, every deploy, idempotently: Drizzle migrations, then `packages/db/src/bootstrap-roles.ts` (creates/repasswords the restricted `kompast_app` role that `DATABASE_URL` points at), then `packages/db/rls.sql`. **This ordering is load-bearing, not cosmetic**: Postgres unconditionally exempts superusers and table owners from row-level security no matter what a policy says, so if the app ever connects using the same role that owns the tables (`DATABASE_ADMIN_URL`'s role), every RLS policy silently does nothing — verified by hand while building this (see git history). `DATABASE_URL` and `DATABASE_ADMIN_URL` must always point at two different roles.

### Backups

Nothing automated exists yet. At minimum, before going anywhere near real data: a `pg_dump` cron with off-box retention, and a documented, *tested* restore procedure — see plan §Deployment, "Ops".
