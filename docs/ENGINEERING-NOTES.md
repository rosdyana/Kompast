# Engineering notes

Implementation rationale, known gotchas, and verification write-ups behind each area of the README — moved here to keep the top-level README short. Read the relevant section before touching that feature area; it exists so a bug already found and fixed doesn't get rediscovered.

## Dev environment

`scripts/dev-services.mjs` (`pnpm dev:docker`) **creates** `kompast-dev-pg`/`kompast-dev-redis` if they don't exist (a fresh clone has no containers to start), starts them if stopped, waits for `pg_isready`/`redis-cli ping` so `turbo run dev` can't race a still-initializing database, and — only on the pass where it had to create the Postgres container — runs `pnpm --filter @kompast/db migrate` for you (a brand-new database has no schema and no `kompast_app` role yet).

- Images are pinned to the same ones `infra/docker-compose.yml` uses: `pgvector/pgvector:pg17` (vanilla `postgres:17` can't `CREATE EXTENSION vector`, which `packages/db/src/migrate.ts` does unconditionally) and `redis:7-alpine`.
- Ports/role/password/db name are read from `.env.local.dev`'s `DATABASE_ADMIN_URL`/`REDIS_URL` rather than hardcoded, so the container and connection string can't drift apart. `.env.local.dev` is the one `.env.*` file that must exist at repo root for this to work (gitignored — a fresh clone has to write it).
- Both bind `127.0.0.1` only; data lives in named volumes, so `docker rm` on a container doesn't lose the database.
- Point either URL at a non-local host and container management is skipped entirely.

## Auth / first run

`apps/web/src/routes/__root.tsx`'s `beforeLoad` checks `system_settings` on every navigation and redirects to `/setup` until Entra ID is configured — deliberate, so a SaaS-style deploy needs infra secrets only, not `.env` edits for business config.

Submitting `/setup` writes encrypted credentials to `system_settings` and invalidates the in-memory Better Auth instance (`apps/web/src/lib/auth.ts`'s `getAuth()`/`invalidateAuthCache()`) — the next request rebuilds it with Microsoft sign-in enabled, no restart needed. `/setup` then permanently redirects to `/login`; re-editing credentials later is a separate admin-gated path on `/settings` (same "blank Client Secret keeps the existing one" convention as the AI/mail sections), calling the same `completeSetup()` and invalidating the auth cache the same way.

**Inviting members** wires up Better Auth's own `organization` plugin invitation API (`createInvitation`/`acceptInvitation`/`rejectInvitation`/`cancelInvitation`/`listInvitations`) rather than building anything custom — the plugin already had a full `invitation` table and endpoints, just never configured with a `sendInvitationEmail` callback. The invitee must already be signed in for `acceptInvitation` to succeed (it checks the accepting session's email against the invitation's) — no first-time-signup handling, so the accept page prompts "sign in with Microsoft" first when there's no session. Not interactively verified end-to-end (no real Entra tenant in dev to complete a real login against). The `sendInvitationEmail` logic itself is covered by a real-Postgres test.

Group-claim → workspace-role mapping (`entra_group_map` table) has no admin UI yet.

**⚠️ Operational gotcha, confirmed by hand (twice — before and after moving Entra config into the DB):** `microsoftEntraId()` always performs live OIDC discovery against `https://login.microsoftonline.com/<tenant>/v2.0/.well-known/openid-configuration` to fetch the JWKS needed for ID-token verification, and its options type has no way to skip or override that. If the tenant is wrong, or Microsoft's discovery endpoint is briefly unreachable, Better Auth's plugin init throws — and because every plugin shares one auth context, **this takes down the entire app, not just Microsoft sign-in**: every route calling `auth.api.getSession()` 500s. Since `/setup` only runs once, a wrong tenant entered there has no UI path to fix — correct `system_settings.microsoft_tenant_id` directly in Postgres, then hit any route once to force `getAuth()` to rebuild (it re-reads settings on every call, only reusing the cache when the read matches what's cached). The underlying fix would be `requireIdTokenVerification: false` on the provider — trading away ID-token signature verification for availability, a security tradeoff intentionally left alone rather than made unilaterally.

## Docs

**Gotcha, hit and fixed by hand:** `@blocknote/react`/`@blocknote/core`/`@blocknote/shadcn`/`@blocknote/server-util`/`@hocuspocus/*` all peer-depend on `yjs`/`y-protocols`/`y-prosemirror`, and pnpm resolved *three different instances* of `@blocknote/core` across the workspace based on differing `y-protocols` versions pulled in transitively. TypeScript correctly flagged this ("separate declarations of a private property"); the root `package.json` pins `y-protocols` via `pnpm.overrides` to collapse most of it, but a couple of call sites in `apps/web/src/components/docs/Editor.tsx` still need a narrow, commented `as any` where TS can't see through the dual-instance history. Not a runtime bug — verified by real Yjs encode/decode round-trip tests in `apps/web/src/lib/__tests__/blocknote-schema.test.ts` and `apps/collab/src/__tests__/server.test.ts`.

Other details: version history snapshots roughly every 5 minutes while a page is edited (in-memory interval, per-process — revisit if the collab tier is ever more than one instance); restoring a version applies blocks through the *live* editor rather than overwriting stored Yjs state directly, to avoid racing anyone currently connected. Guest share links render content server-side from stored Yjs bytes via `@blocknote/server-util`, and always replace a `kompastView` embed with a placeholder first — BlockNote attaches every block's props as raw `data-*` HTML attributes regardless of render function, so the only reliable way to keep an embed's board/view IDs out of guest-facing HTML is to never hand that block to the exporter at all.

## REST API + MCP

**Gotcha, hit and fixed by hand:** `@blocknote/server-util` (used to render page content as Markdown for REST/MCP) depends on `jsdom`, which cannot be bundled into Nitro's otherwise-self-contained SSR output — one of its internal CJS modules reads its own default stylesheet via a `__dirname`-relative path, and every request 500'd once that got relocated into a bundled chunk. Found via a real `docker build` + `docker run`, not `pnpm build` (dev server and `vitest` never touch the built Nitro output, so this class of bug is invisible to either). Fixed by declaring `jsdom` as a direct `apps/web` dependency (pnpm's isolation otherwise hides it as a phantom transitive dep), marking it external in `vite.config.ts`'s `nitro.rollupConfig`, and having `infra/Dockerfile.web` run `pnpm deploy --prod --legacy` so the runtime image gets a real, non-symlinked `node_modules` for it instead of only the bundled `.output`.

MCP is stateless (a fresh server is built per request, scoped to that request's authenticated token — no session, so it needs no session affinity behind a reverse proxy). A missing token scope comes back as a tool-level error, not an HTTP 403 — one `/mcp` POST is one JSON-RPC call, so there's no earlier point to reject a specific tool's scope requirement. `pages` PATCH is deliberately metadata-only (title/icon) — overwriting a page's Yjs document from outside its collab session would race with anyone live-editing it.

## Sprints & roadmap

`sprint_issue` is membership *history*, not just current state, so scope added mid-sprint is distinguishable from what was originally planned. There's no nightly snapshot cron for burndown yet — `apps/worker`'s queue infra isn't wired to sprint snapshots, so reports are reconstructed on read from `sprint_issue` + `issue_history`. An epic is just an issue whose type has `hierarchyLevel = 0` (not matched by name, since that row can be renamed). The sprint-review `TableView` reuse (`SprintReviewTable` in `$projectKey.tsx`) is currently unreferenced — a later pass wires it into a sprint-scoped Table tab. Every board now requires at least one sprint before use; opening Board/Backlog with zero sprints shows a setup wizard instead of normal tab content.

## Notifications & mail

**Gotcha, hit and fixed by hand:** `apps/worker`'s build had to switch from ESM to CJS output after two real bundling bugs, found one at a time via an actual `node dist/...` run: `ioredis` (and its `node-abort-controller` dependency) do computed/deep-subpath `require(...)` calls esbuild can't turn into ESM imports ("Dynamic require of ... is not supported"), and even once excluded from the bundle, Node's own ESM loader refuses to resolve their extensionless deep imports (`ERR_UNSUPPORTED_DIR_IMPORT`) — a strictness plain CJS `require()` doesn't have. CJS sidesteps both.

Mail delivery is a transactional outbox (`email_outbox` written in the same transaction as whatever triggered it), polled every 15s by `apps/worker` — worst-case delivery latency is that interval, fine for notification email, not for anything latency-sensitive.

## Automation

**Verified**: a real `docker build`+`docker run` of both `kompast-web` and `kompast-worker` images against the dev Postgres/Redis — created a rule and an issue over the live REST API, transitioned the issue, and confirmed the containerized worker's automation queue picked up the resulting `issue.transitioned` event within one poll interval, applied the `add_label` action, and logged a `matched` run visible through `GET .../runs` — end to end, no mocking.

Guardrails: max chain depth 5 (an event at/past that depth is skipped with no run logged); a rule never re-fires on the event its own action just caused, though other rules still see it; a per-rule rate limit (50 matched runs/hour); dry-run mode; every candidate rule evaluated against every event gets an `automation_run` row, including `not_matched`/`skipped_rate_limited`, not just fired ones.

## AI assist

Doc writing assist always inserts as a new block after the current one — never an in-place rewrite — a deliberate simplification so every action (continue/improve/shorten/expand/summarize/translate) shares one code path.

**Verified**: `pnpm typecheck && pnpm build && pnpm test` green across all packages (20 tests against a mocked `fetch` — no real provider call/cost — covering every driver's request shape, SSE parsing including a frame split across two chunk reads, and config-validation errors per provider); `runAiCompletion`/`runDocTextAction`/`generateIssueDescription`/`generateSprintSummary` covered end-to-end against a real Postgres with a mocked Anthropic SSE response; a real `docker build`+`docker run` confirmed `/api/ai/stream` 405s on GET and 401s an unauthenticated POST. **Not verified**: the interactive browser flows (slash-menu items, Sprint tab button) against a real LLM call — no real Entra tenant or live provider key in this environment, and spending one to self-verify wasn't a call to make unilaterally. Treat the doc-editor and sprint-summary UI as needing a human smoke test before relying on them in production.

## Ask Kompast (RAG chat)

Built in two stages, verified independently: issues/comments now, docs/pages later (stage B).

- Postgres image switched to `pgvector/pgvector:pg17`; `packages/db/src/migrate.ts` runs `CREATE EXTENSION IF NOT EXISTS vector` before migrations. Embedding dimension (1536, matching OpenAI/Azure's `text-embedding-3-small`) is fixed at the column level — changing models later means a migration plus full reindex.
- A separate embedding provider from the chat provider — Anthropic has no public embeddings API, so `/settings` has an independent "Embedding (Ask Kompast)" section (Azure OpenAI or OpenAI-compatible only).
- Indexing chunks text (paragraph-aware, ~1000 chars/chunk) and replaces any existing chunks for that entity wholesale. Reindexing is a transactional outbox, same pattern as `email_outbox`/`automation_event` — including for `origin: "import"` (bulk-imported issues should be just as findable as live-created ones, unlike notifications/automation, which imports never fire).
- An indexed issue's text includes its sprint's name/goal *at the time it was last (re)indexed* — moving an issue between sprints does not itself trigger a reindex (would create a real circular import between `sprint.ts`/`rag.ts`/`ai.ts` for a freshness improvement judged not worth the risk). Context goes stale until the issue is next edited.
- No live tool-calling for numeric sprint state (burndown/velocity) — a deliberate scope decision: that data goes stale immediately if embedded and doesn't benefit from semantic search. The right architecture is a tool-call the assistant invokes on demand, reusing P4's report functions — not built this pass, and `packages/ai`'s driver interface doesn't support function/tool-calling at all yet.
- Docs/pages indexing (stage B) isn't built: page content lives as Yjs binary state, and converting it to text needs `@blocknote/server-util` → `jsdom`, the exact library that broke Nitro bundling in P3 (see REST API + MCP above). Sequenced as a separate, independently-Docker-verified step rather than risking two unknowns at once. Also not built: permission-filtered retrieval (needed once pages, which have per-page restrictions, are indexed), a full-reindex admin action, and any REST/MCP surface for Ask Kompast.
- **Verified**: real-Postgres tests cover chunking, wholesale chunk replacement, the full enqueue→claim→process pipeline, similarity-ordered search (a deterministic hash-based fake embedding stands in for a real model), and `askKompast`'s end-to-end behavior (retrieval, generation, persistence, citations, thread continuation, the not-configured error). Found and fixed one real bug while writing these: the reindex queue is claimed system-wide, so asserting against `claimPendingReindexTasks(...)[0]` raced other concurrently-running test files — fixed by filtering the claimed batch by a known id instead of assuming position. A real `docker build`+`docker run` confirmed `/api/ask/stream` 405s on GET/401s an unauthenticated POST, and a real issue created against a deliberately-unreachable embedding endpoint produced a genuine DNS failure the worker's reindex queue caught and recorded correctly (proving the failure path since no real embedding credentials exist in this environment).

## Importers

- `packages/import`: extract → map → load, one source folder per importer (`src/jira/`). `fetchJiraIssues()` pages JIRA Cloud's real search API until exhausted; `parseJiraExportFile()` reads the same shape from a checked-out JSON export as a fallback with no live API call. Status/type mapping trusts JIRA's own `statusCategory.key` directly — no human-confirms-the-mapping UI step yet; the dry-run report is the only review surface today.
- A run creates missing statuses/types, creates every issue not already linked via `external_ref` (idempotency key: `(organizationId, "jira", jiraIssueKey)`), backfills parent linkage in a second pass, and — only for issues newly created *this run* — loads comments, worklogs, outward issue links, attachments (if a download callback is supplied), and changelog-derived historical status transitions as backdated `issue_history` rows (deliberately not `moveIssue`, which would also mutate current status). Every issue is wrapped in its own try/catch — one bad issue's error lands in the report, not a killed run.
- `fixVersions`/`components` land in `issue.customFields.jira` rather than first-class rows — deliberate, not a placeholder; giving them their own management surface is a separate, unscheduled feature.
- `adfToPlainText()` is a best-effort, lossy walk of JIRA's Atlassian Document Format (drops formatting, never throws on an unrecognized node) rather than a strict renderer.
- Every write uses `origin: "import"`, suppressing notifications and automation entirely (importing 5,000 historical issues must not send 5,000 emails or fire live rules).
- Imports run **synchronously in the request** — no background job/queue exists for them; a very large project may exceed a reverse-proxy timeout, a known limitation rather than something this pass builds around.
- Email→Kompast-user resolution: gathers every distinct reporter/assignee/comment-author/worklog-author email across the batch and resolves each once against members before the load pass. No match just leaves the field unset — no directory sync.
- **Verified**: a golden-fixture test (3-issue fixture with a parent/subtask pair, cross-issue link, comment, worklog, changelog transition) against a real Postgres — dry-run writes nothing; a real run creates all 3 issues, resolves the parent link, gets every count right; running the same import twice creates zero duplicates. REST tests mock JIRA's search response for create/dry-run/list/detail/scope-rejection paths. A real `docker build`+`docker run` confirmed the create→run→fail→readable-via-GET lifecycle against a genuinely unreachable host — no real JIRA account exists in this environment to test the success path against a live server, so that rests on the mocked-fetch tests alone.
- **Not built at all**: the Notion importer (extractor, block-type→BlockNote converter, internal-link rewrite, incremental-sync worker job); any background job/queue for long-running imports; a human-confirms-the-status-mapping UI step; a live-JIRA-auth test for attachment streaming; and the fuller reconciliation report the original plan describes (today it's just counts, not "unresolved links, skipped blocks").
- Credentials needed ahead of a real run: JIRA Cloud email + API token; Notion internal integration token (not used yet, importer doesn't exist).
