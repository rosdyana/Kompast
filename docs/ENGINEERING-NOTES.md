# Engineering notes

Implementation rationale, known gotchas, and verification write-ups behind each area of the README — moved here to keep the top-level README short. Read the relevant section before touching that feature area; it exists so a bug already found and fixed doesn't get rediscovered.

## Dev environment

`scripts/dev-services.mjs` (`pnpm dev:docker`) **creates** `kompast-dev-pg`/`kompast-dev-redis` if they don't exist (a fresh clone has no containers to start), starts them if stopped, waits for `pg_isready`/`redis-cli ping` so `turbo run dev` can't race a still-initializing database, and — only on the pass where it had to create the Postgres container — runs `pnpm --filter @kompast/db migrate` for you (a brand-new database has no schema and no `kompast_app` role yet).

- Images are pinned to the same ones `infra/docker-compose.yml` uses: `pgvector/pgvector:pg17` (vanilla `postgres:17` can't `CREATE EXTENSION vector`, which `packages/db/src/migrate.ts` does unconditionally) and `redis:7-alpine`.
- Ports/role/password/db name are read from `.env.local.dev`'s `DATABASE_ADMIN_URL`/`REDIS_URL` rather than hardcoded, so the container and connection string can't drift apart. `.env.local.dev` is the one `.env.*` file that must exist at repo root for this to work (gitignored — a fresh clone has to write it).
- Both bind `127.0.0.1` only; data lives in named volumes, so `docker rm` on a container doesn't lose the database.
- Point either URL at a non-local host and container management is skipped entirely.

## Auth / first run

`apps/web/src/routes/__root.tsx`'s `beforeLoad` checks `system_settings` on every navigation and redirects to `/setup` until Entra ID is configured — deliberate, so a SaaS-style deploy needs infra secrets only, not `.env` edits for business config.

Submitting `/setup` writes encrypted credentials to `system_settings` and invalidates the in-memory Better Auth instance (`apps/web/src/lib/auth.ts`'s `getAuth()`/`invalidateAuthCache()`) — the next request rebuilds it with Microsoft sign-in enabled, no restart needed. `/setup` then permanently redirects to `/login`; re-editing credentials later is a separate admin-gated path on `/settings` (same "blank Client Secret keeps the existing one" convention as the AI/mail sections), calling the same `completeSetup()` and invalidating the auth cache the same way.

**Inviting members** wires up Better Auth's own `organization` plugin invitation API (`createInvitation`/`acceptInvitation`/`rejectInvitation`/`cancelInvitation`/`listInvitations`) rather than building anything custom — the plugin already had a full `invitation` table and endpoints, just never configured with a `sendInvitationEmail` callback. The invitee must already be signed in for `acceptInvitation` to succeed (it checks the accepting session's email against the invitation's) — no first-time-signup handling, so the accept page prompts "sign in with Microsoft" first when there's no session. Not interactively verified end-to-end (no real Entra tenant in dev to complete a real login against). The `sendInvitationEmail` logic itself is covered by a real-Postgres test.

Group-claim → workspace-role mapping (`entra_group_map` table) has no admin UI yet.

**Deployment admin vs workspace admin.** `system_settings` (Entra, AI, embedding, mail) is one row shared by every workspace, so it is gated by `requireDeploymentAdmin` (`packages/core/src/settings.ts`): the super admin of the *founding* workspace (oldest `organization`), not owner/admin of whatever workspace the caller is in. Workspace-scoped tabs (members, general) keep `requireSystemAdmin`. `/settings` hides the Integrations group from everyone else. Changing an AI/embedding endpoint or provider, or the mail driver, requires re-entering the key — a stored key is never sent to a new host.

**Better Auth's plugin REST surface is closed.** `hooks.before` in `apps/web/src/lib/auth.ts` rejects any HTTP request to `/api/auth/organization/*` and `/api/auth/api-key/*` (403); `allowUserToCreateOrganization: false` on top. Those endpoints only know Better Auth's roles, so over HTTP a user could create their own workspace, a workspace admin could join any team (which is what RLS keys project visibility on), and anyone could mint a PAT outside `server-fns/tokens.ts`. The browser only signs in/out; every org/team/invitation/key operation is a server function that applies Kompast's gates and then calls `auth.api.*` directly — a direct call has no `ctx.request`, so the hook ignores it. If a new feature needs one of these endpoints from the browser, add a server function instead of loosening the hook.

**Password sign-in exists in two gated forms**: the local-only dev-admin bypass (`ENABLE_DEV_LOGIN`, never with `NODE_ENV=production`) and stakeholder demo mode (see Demo mode below). Real deployments are Entra-only.

**⚠️ Operational gotcha, confirmed by hand (twice — before and after moving Entra config into the DB):** `microsoftEntraId()` always performs live OIDC discovery against `https://login.microsoftonline.com/<tenant>/v2.0/.well-known/openid-configuration` to fetch the JWKS needed for ID-token verification, and its options type has no way to skip or override that. If the tenant is wrong, or Microsoft's discovery endpoint is briefly unreachable, Better Auth's plugin init throws — and because every plugin shares one auth context, **this takes down the entire app, not just Microsoft sign-in**: every route calling `auth.api.getSession()` 500s. Since `/setup` only runs once, a wrong tenant entered there has no UI path to fix — correct `system_settings.microsoft_tenant_id` directly in Postgres, then hit any route once to force `getAuth()` to rebuild (it re-reads settings on every call, only reusing the cache when the read matches what's cached). The underlying fix would be `requireIdTokenVerification: false` on the provider — trading away ID-token signature verification for availability, a security tradeoff intentionally left alone rather than made unilaterally.

## Teams & visibility

Design and decisions: `docs/superpowers/specs/2026-10-12-team-scoped-visibility-design.md`.

**Enforced in RLS, not per route.** `packages/db/rls.sql` scopes `project` to `kompast_is_super_admin() or team_id in (select kompast_my_team_ids())`. Every project-owned table filters through `select id from project` (or `issue`/`sprint`/`page`), and Postgres applies the inner table's own policy inside a policy subquery, so issues, comments, worklogs, links, attachments, history, sprints, automation workflows, import runs and embeddings all inherit team scoping. Nothing in REST, MCP or the server functions filters by team; a missed filter fails closed. `team_id IS NULL` (legacy) projects are super-admin-only. Pages: project pages follow their project; team-space pages (`page.team_id`) follow the team; pages with neither are the shared Workspace space. `page_single_space_ck` forbids both, and `packages/core/src/page.ts` keeps a whole subtree in one space.

**Gotchas hit while building it:**
- `canAccessPage` used to return `true` for a page the caller couldn't see. RLS hides its `page_permission` rows too, so it looked "unrestricted". It now checks the page row is visible first.
- Child-policy inheritance applies to *writes* as well: USING doubles as WITH CHECK, and UPDATE/DELETE apply the SELECT policy to their WHERE clause. That's why RAG indexing (`apps/worker` reindex) moved from "withAuthorizedTenant as the first member found" to `withTenant(adminDb, …)`, the same shape automation already used. An arbitrary member may not see the entity being indexed. Retrieval still runs as the asking user, which is what keeps other teams' text out of Ask Kompast.
- `page.team_id` is `ON DELETE NO ACTION`, not `RESTRICT`. RESTRICT is checked immediately and broke deleting a whole organization (the same cascade removes both team and pages). `SET NULL` would fail open by moving private pages into the Workspace space.
- Anything delivered to *another* user must re-check visibility for that user, because the transaction's RLS identity is the actor's. `notify()` does this (`canUserSeeEntity`), and project assignee pickers use `listAssignableUsers` (team + super admin).
- REST/MCP page create must pass `projectId: undefined`, not `null`, when no `projectKey` is given. `null` means "force the Workspace space", which `createPage` rejects under a project parent.

**Team invitations** write Better Auth's `invitation` row directly (`createTeamInvitation`), for the same reason `addTeamMember` bypasses the plugin: its endpoint checks the caller's *workspace* role, which can't express "this team's admin". The plugin's real `acceptInvitation` still does accepting (email match, expiry, member + team_member rows); `applyAcceptedTeamInvitation` then applies Kompast's own `invitation.team_role`. Invitees always get workspace role `member`. **Not verified end-to-end:** the accept step needs a signed-in invitee, which neither tests (no session) nor demo mode (sign-up closed) can provide. The core half is tested with the plugin's effects simulated.

**Renaming and deleting.** Team admins rename their own team (`renameTeam`, names unique per workspace case-insensitively, app-checked because Better Auth's `createTeam` also writes the table). Workspace owner/admins rename the workspace from Settings → General (`renameWorkspace`, display name only; the slug is left alone). Deleting a team is super-admin only (`deleteTeam`). A team that still owns projects or live team docs must name a `transferToTeamId`, and everything moves there in the same transaction first. The FKs can't be trusted to handle it: `project.team_id` SET NULL would silently make the projects super-admin-only, and `page.team_id` NO ACTION would just fail. Projects move through `assignProjectToTeam`, so a key clash in the target aborts the whole delete. Pending team invitations are canceled explicitly, because `invitation.team_id` SET NULL would otherwise turn them into live workspace-only invites. With no target, trashed team docs are deleted along with the team. `entra_group_map.team_id` is left to SET NULL, so the group still grants workspace membership. No REST/MCP surface yet; only server functions.

**Not built:** request-access flow; REST/MCP for team/workspace rename+delete; RLS on config tables (`board`, `board_column`, `workflow_status`, `issue_type`, `saved_view`), which are only reachable by id but aren't policy-protected; force-closing a live collab socket when someone leaves a team (the 60s token TTL bounds reconnects only); per-project roles beyond `lead`.

**Private & Shared spaces** (Notion's "Private" and "Shared" sidebar sections). `page.private_owner_id` is a fourth space next to project/team/Workspace; `page_single_space_ck` (`num_nonnulls(...) <= 1`) allows at most one. The page RLS policy admits a personal page to its owner, to the people in `page.shared_with`, or to the super admin when the owner is no longer a member, and to nobody else. There's deliberately no blanket `kompast_is_super_admin()` branch, because Notion's private pages "can't be seen by the people in your workspace". USING doubles as WITH CHECK, so nobody can create or move a page into someone else's personal space. Adapters only take `private: boolean` and set the owner to the caller.

- **Why `shared_with` is denormalized.** The page policy can't read `page_permission`: that table's policy reads `page`, and Postgres rejects mutually recursive policies. A SECURITY DEFINER helper doesn't help either: with FORCE RLS the table owner is still subject to RLS unless it's a superuser or has BYPASSRLS, and the deploy-time admin role isn't guaranteed to be either (Cloud SQL, for one). So `shared_with text[]` on every page of a Shared tree is the visibility list (GIN-indexed, `@>`), and `page_permission` rows on the tree's root still hold the roles. Only `syncSharedWith` in `page-permission.ts` writes it, re-deriving it from the root's user grants after every grant or removal. `shared_with` is part of `PageSpace`, so children and moved subtrees inherit it through the existing `resolveSpace`/`movePage` path.
- **Roles are per tree, on the root.** Like Notion's sub-pages inheriting their parent's permissions, `personalPageRole` looks up the caller's grant on `treeRootId`. Invitees default to view if a grant is somehow missing. A sub-page pulled to the top of a Shared space copies the old root's grants with it. Teams can't be invited (a Shared page is between people). Use a team space for that.
- **Leaving a personal space** (move or drag to a team/Workspace/project) deletes the subtree's grants. Invitations must not become a restriction that locks out the owner, who never had a grant row. **Entering Private** also revokes live guest links, since "only me" should mean only me. Publishing it again afterwards is an explicit choice. Any move into or out of a personal space (Move to…, or dragging under a page in another space) needs `canManagePageAccess`, not just edit. Duplicating a personal page puts the copy in the copier's own Private space.
- **You can't remove yourself from a Shared page.** The UPDATE that drops you from `shared_with` would leave the row invisible to you, and WITH CHECK refuses that. Core throws a clear `PageSpaceError` first. Ask the owner, or have someone with full access remove you.
- **Departed members** (`page-recovery.ts`, Settings → Departed members' pages, super admin only). Once a Private/Shared page's owner is no longer in `member`, RLS lets the super admin see it. "Take ownership" makes them the owner and keeps any invitees. "Move to Workspace" moves it to Workspace. Both write `audit_log`, its first writer in the codebase. Invitees keep access until it's recovered. A current member's private pages stay invisible to the super admin. `private_owner_id` cascades on user delete, so deleting the user row (not just the membership) deletes their personal pages.
- `canUserSeeEntity` checks owner/`shared_with` *before* its super-admin shortcut, so notifications never fan out about someone else's private page. Sharing notifies each new invitee (`page.shared`).

Proof: `packages/core/src/__tests__/private-space.test.ts` and the private-page test in `apps/web/src/routes/api/v1/__tests__/pages.test.ts`.

**Not built (personal pages):** a "leave this shared page" action (see above for why it needs a policy split per command); sharing with guests from outside the workspace (only guest links); per-sub-page overrides inside a Shared tree (Notion allows them; here a tree has one access list).

## Demo mode

`DEMO_MODE` + `DEMO_ACCESS_CODE` (`apps/web/src/lib/demo.ts`). Unlike dev login it works with `NODE_ENV=production`, because a hosted demo runs the real images. Demo personas' password *is* the access code, sign-up stays disabled (`emailAndPassword.disableSignUp`), and `/setup`'s Entra gate is skipped. `apps/web/scripts/seed-demo.ts` creates personas through a seed-only Better Auth instance with sign-up open, so the credential rows are exactly what sign-in later reads (Better Auth 1.7's `account.issuer` etc.), then builds the dataset through `packages/core` as the persona who'd really do each thing. The only direct writes backdate timestamps so a sprint can be "a week in". **Gotcha:** `turbo.json`'s `globalPassThroughEnv` must list every env var the apps read; turbo silently drops undeclared ones, and `DEMO_MODE` read as off until it was added. Runbook: `docs/DEMO.md`.

## Docs

**Gotcha, hit and fixed by hand:** `@blocknote/react`/`@blocknote/core`/`@blocknote/shadcn`/`@blocknote/server-util`/`@hocuspocus/*` all peer-depend on `yjs`/`y-protocols`/`y-prosemirror`, and pnpm resolved *three different instances* of `@blocknote/core` across the workspace based on differing `y-protocols` versions pulled in transitively. TypeScript correctly flagged this ("separate declarations of a private property"); the root `package.json` pins `y-protocols` via `pnpm.overrides` to collapse most of it, but a couple of call sites in `apps/web/src/components/docs/Editor.tsx` still need a narrow, commented `as any` where TS can't see through the dual-instance history. Not a runtime bug — verified by real Yjs encode/decode round-trip tests in `apps/web/src/lib/__tests__/blocknote-schema.test.ts` and `apps/collab/src/__tests__/server.test.ts`.

Other details: version history snapshots roughly every 5 minutes while a page is edited (in-memory interval, per-process — revisit if the collab tier is ever more than one instance); restoring a version applies blocks through the *live* editor rather than overwriting stored Yjs state directly, to avoid racing anyone currently connected. Guest share links render content server-side from stored Yjs bytes via `@blocknote/server-util`, and always replace a `kompastView` embed with a placeholder first — BlockNote attaches every block's props as raw `data-*` HTML attributes regardless of render function, so the only reliable way to keep an embed's board/view IDs out of guest-facing HTML is to never hand that block to the exporter at all.

## REST API + MCP

**Gotcha, hit and fixed by hand:** `@blocknote/server-util` (used to render page content as Markdown for REST/MCP) depends on `jsdom`, which cannot be bundled into Nitro's otherwise-self-contained SSR output — one of its internal CJS modules reads its own default stylesheet via a `__dirname`-relative path, and every request 500'd once that got relocated into a bundled chunk. Found via a real `docker build` + `docker run`, not `pnpm build` (dev server and `vitest` never touch the built Nitro output, so this class of bug is invisible to either). Fixed by declaring `jsdom` as a direct `apps/web` dependency (pnpm's isolation otherwise hides it as a phantom transitive dep), marking it external in `vite.config.ts`'s `nitro.rollupConfig`, and having `infra/Dockerfile.web` run `pnpm deploy --prod --legacy` so the runtime image gets a real, non-symlinked `node_modules` for it instead of only the bundled `.output`.

MCP is stateless (a fresh server is built per request, scoped to that request's authenticated token — no session, so it needs no session affinity behind a reverse proxy). A missing token scope comes back as a tool-level error, not an HTTP 403 — one `/mcp` POST is one JSON-RPC call, so there's no earlier point to reject a specific tool's scope requirement. `pages` PATCH is deliberately metadata-only (title/icon) — overwriting a page's Yjs document from outside its collab session would race with anyone live-editing it.

**MCP coverage.** MCP is a superset of `/api/v1`: everything REST does, plus the issue and doc work the UI does that REST doesn't (yet). Issues: create/update (epic, parent, sprint, type, estimate), transition, assign, comment and list comments, custom properties, issue↔issue links, worklogs, checklist, watching, archive/restore, backlog, and an enriched `get_issue` (type/status names, plain-text description, checklist, links, linked docs). `get_project` returns the types, statuses, priorities, properties, epics and assignable members, so an agent can fill those fields without guessing. Sprints: create, rename, start, complete, membership, report, burndown/CFD, velocity. Docs: create, read (Markdown), title search, move (nest or change space), duplicate/new-from-template, template flag, trash/restore/permanent delete, versions (read-only), comments and resolve, page↔issue links, favorites, access lists. Automation workflows (create/update/delete, runs) and the caller's notifications. Permission checks match the UI's: moving a page into or out of Private needs `canManagePageAccess`, archiving an issue needs project admin. Duplicating a *restricted* page also needs `canManagePageAccess`, because `duplicatePage` doesn't copy the access list, so the copy would be open to the whole space. `list_teams` and the notification tools need no scope, like `whoami`.

**Deliberately not on MCP:** writing page content or restoring a version (races the live collab session, see above); guest share links (publishing a page to anyone with the URL stays a human action); attachment upload (a file body doesn't fit a tool call); imports (JIRA needs credentials and runs synchronously; Notion is a zip upload); Ask Kompast (spends AI-provider tokens, and has no REST surface either); and admin/config (projects, teams, members, board columns, statuses, priorities, property definitions, settings).

**Gotcha, hit and fixed by hand:** `@better-auth/api-key` rate-limits each key to **10 requests per 24 hours** by default, and stamps that onto the `apikey` row when the key is created. Every PAT was unusable after ten calls; one MCP session (initialize, tools/list, a few calls) burns that. No test caught it because each test minted fresh keys and made fewer than ten calls. Fixed with `rateLimit: { enabled: false }` on the plugin in `apps/web/src/lib/auth.ts`. Only the plugin-level switch overrides the per-row values already stored on existing keys. Throttling, if wanted, belongs at the reverse proxy.

**Page access in the UI server functions (was a known gap, fixed in the security pass):** every page mutation in `apps/web/src/lib/server-fns/pages.ts` now runs the same core gate MCP/REST use — `requirePageAccess` (edit for meta/move/archive/restore/template/links/issue-from-line, comment for comments, full for permanent delete), `requireCanCopyPage` (duplicate / new-from-template: a restricted source needs `canManagePageAccess`), and `requireCanManagePageAccess` for creating or revoking a guest share link (a link publishes the page outside the workspace). All three live in `packages/core/src/page-permission.ts`. A trashed page's share link stops resolving until it is restored.

## Sprints & roadmap

`sprint_issue` is membership *history*, not just current state, so scope added mid-sprint is distinguishable from what was originally planned. There's no nightly snapshot cron for burndown yet — `apps/worker`'s queue infra isn't wired to sprint snapshots, so reports are reconstructed on read from `sprint_issue` + `issue_history`. An epic is just an issue whose type has `hierarchyLevel = 0` (not matched by name, since that row can be renamed). The sprint-review `TableView` reuse (`SprintReviewTable` in `$projectKey.tsx`) is currently unreferenced — a later pass wires it into a sprint-scoped Table tab. Every board now requires at least one sprint before use; opening Board/Backlog with zero sprints shows a setup wizard instead of normal tab content.

## Notifications & mail

**Gotcha, hit and fixed by hand:** `apps/worker`'s build had to switch from ESM to CJS output after two real bundling bugs, found one at a time via an actual `node dist/...` run: `ioredis` (and its `node-abort-controller` dependency) do computed/deep-subpath `require(...)` calls esbuild can't turn into ESM imports ("Dynamic require of ... is not supported"), and even once excluded from the bundle, Node's own ESM loader refuses to resolve their extensionless deep imports (`ERR_UNSUPPORTED_DIR_IMPORT`) — a strictness plain CJS `require()` doesn't have. CJS sidesteps both.

Mail delivery is a transactional outbox (`email_outbox` written in the same transaction as whatever triggered it), polled every 15s by `apps/worker` — worst-case delivery latency is that interval, fine for notification email, not for anything latency-sensitive.

## Automation

**Who can change workflows, and what they can touch.** Creating, editing, enabling/disabling and deleting a workflow needs project admin/lead (`requireWorkflowManager` in `packages/core/src/automation-workflow.ts`, called by the UI, REST and MCP adapters). At run time every issue-touching node goes through `requireScopedIssueId` (`automation-execution.ts`): the issue must be in the workflow's own project. This matters because the worker runs on the admin connection (RLS does not apply) and a `loop_each` can iterate a user-typed list of issue ids. `action_link_issue`'s target must be in the same workspace.

The original flat rule engine (`automation_rule`/`automation_run`/`automation_event`, one trigger + ANDed conditions + an action list per row) was fully replaced by a node-graph workflow engine (`automation_workflow`/`automation_node`/`automation_edge` + a durable per-node run/step trail) and its React Flow canvas UI, in one cutover: a one-off script converted every existing `automation_rule` row into an equivalent linear `automation_workflow` graph (reusing the rule's own id as the workflow id), then the old tables were dropped and the old engine/REST routes (`/api/v1/automation/rules*`)/server-fns/UI tab were deleted outright — no compatibility shim, per the design doc's "Migrating existing rules" section.

Node types: `trigger_event`/`trigger_schedule` (cron), `condition_property` (if/else) and `condition_switch` (multi-way, case labels as edge handles), the original 7 action types (`action_set_property`/`add_label`/`comment`/`notify`/`link_issue`/`create_subtask`/`webhook`) plus `find_issues` + `loop_each` (a schedule-triggered workflow's only path to touching issues, since a schedule tick has no triggering issue of its own — see `resolveIssueId` in `automation-execution.ts`), and `delay`. Data flows between nodes via `{{trigger.payload.x}}` / `{{steps.<name>.output.x}}` / `{{item}}` template expressions (dot-path substitution only, deliberately no JS `eval` — this engine already has an SSRF-guarded outbound-webhook action reachable by any `issues:write` user, so a second arbitrary-code-execution surface on top of that would be a real regression, not just scope creep).

Guardrails, unchanged in spirit from the old engine: max chain depth 5 (tracked per-step, a branch past it is `skipped_max_depth` without stopping sibling branches from the same fan-out); a workflow never re-fires on the event its own action just caused (`causedByWorkflowId`), though other workflows still see it; a per-workflow rate limit (50 runs/hour); dry-run mode (`action_*` nodes compute and log without applying); `loop_each` additionally caps fan-out width at `MAX_LOOP_ITERATIONS` (200) and `find_issues` at `MAX_FIND_ISSUES_RESULTS` (500) issues per call.

**Verified**: `pnpm typecheck`/`vitest run` green across the whole workspace (packages/core's automation suite alone: 65 tests across expression resolution, per-node execution, engine fan-out/branching/loop/schedule integration, and graph validation — all real-Postgres, no mocked DB); a real `docker build`+`docker run` of both `kompast-web` and `kompast-worker` images against the dev Postgres/Redis confirmed both start clean with zero errors, the new `/api/v1/automation/workflows` REST route responds (401 unauthenticated, not a 500), and — with the containerized worker as the *only* worker process running — creating a real issue through the app produced a `completed` run visible in the canvas's Run History panel within the worker's poll interval; a full manual browser session (Playwright-driven) additionally covered create-workflow → drag a node from the palette → connect trigger to it by dragging handle-to-handle → configure it in the side panel → Save → reload → confirm the graph and config persisted exactly → toggle enabled/dry-run.

**Not carried over from the old engine's flat model**: nothing — this is a strict superset (branching was if/else-only before, now if/else + multi-way switch; no schedule trigger before; no cross-node data passing before).

## AI assist

Doc writing assist always inserts as a new block after the current one — never an in-place rewrite — a deliberate simplification so every action (continue/improve/shorten/expand/summarize/translate) shares one code path.

**Verified**: `pnpm typecheck && pnpm build && pnpm test` green across all packages (20 tests against a mocked `fetch` — no real provider call/cost — covering every driver's request shape, SSE parsing including a frame split across two chunk reads, and config-validation errors per provider); `runAiCompletion`/`runDocTextAction`/`generateIssueDescription`/`generateSprintSummary` covered end-to-end against a real Postgres with a mocked Anthropic SSE response; a real `docker build`+`docker run` confirmed `/api/ai/stream` 405s on GET and 401s an unauthenticated POST. **Not verified**: the interactive browser flows (slash-menu items, Sprint tab button) against a real LLM call — no real Entra tenant or live provider key in this environment, and spending one to self-verify wasn't a call to make unilaterally. Treat the doc-editor and sprint-summary UI as needing a human smoke test before relying on them in production.

## Ask Kompast (RAG chat)

Covers issues, comments and docs/pages, plus read-only tool calls for structured questions. Originally built in two stages (issues/comments first, then docs).

- Postgres image switched to `pgvector/pgvector:pg17`; `packages/db/src/migrate.ts` runs `CREATE EXTENSION IF NOT EXISTS vector` before migrations. Embedding dimension (1536, matching OpenAI/Azure's `text-embedding-3-small`) is fixed at the column level — changing models later means a migration plus full reindex.
- A separate embedding provider from the chat provider — Anthropic has no public embeddings API, so `/settings` has an independent "Embedding (Ask Kompast)" section (Azure OpenAI or OpenAI-compatible only).
- Indexing chunks text (paragraph-aware, ~1000 chars/chunk) and replaces any existing chunks for that entity wholesale. Reindexing is a transactional outbox, same pattern as `email_outbox`/`automation_event` — including for `origin: "import"` (bulk-imported issues should be just as findable as live-created ones, unlike notifications/automation, which imports never fire).
- **The index holds only text that changes when the text changes.** Issue index text is title + description; it no longer folds in the sprint name (that went stale on every sprint move). Status, assignee, priority, sprint and labels are read *live* at answer time instead (`packages/core/src/rag-enrich.ts`, `enrichCandidates`), as the asking user, and written into a one-line header above each retrieved chunk. A candidate whose entity doesn't come back from that read (invisible or deleted) is dropped from both the prompt and the citations.
- **Queue dedup.** `enqueueReindex` (`packages/core/src/rag-queue.ts`, exported as `@kompast/core/rag-queue` so `apps/collab` can use it without pulling in `@kompast/ai`) skips the insert when a *pending* task for the same entity+action exists. A task already in `processing` doesn't block a new one, since it may have read content before the latest edit. This is what makes enqueueing on every collab save affordable.
- **Archived content** is filtered at query time in `searchEmbeddings` (archived issue, comment on an archived issue, archived page), not by hooking every archive path — UI, MCP and JIRA sync all archive differently.
- **JIRA sync** writes some issue/comment text directly rather than via `updateIssue`/`addComment`; those spots in `packages/import/src/jira/load.ts` and `inline-attachments.ts` enqueue a reindex themselves.
- **Docs/pages.** Page text is extracted with plain `yjs` (`packages/core/src/ydoc-text.ts`), walking BlockNote's `document-store` fragment by node name — deliberately *not* `@blocknote/server-util`, whose `jsdom` dependency broke bundling before (see REST API + MCP above). Observed structure: `blockGroup > blockContainer > <block> > XmlText`; tables are `table > tableRow > (tableHeader | tableCell) > tableParagraph`; `kompastView` embeds are skipped. Pages are enqueued from `apps/collab`'s `onStoreDocument` (every debounced save, collapsed by the dedup above), `createPage`, `updatePageMeta` (title only), `permanentlyDeletePage` (`action: "delete"` — `embedding` has no FK to `page`), Notion import and demo seeding. Version restore goes through the live editor, so `onStoreDocument` covers it. Visibility (team/project/private/shared) is entirely the `embedding` RLS policy deferring to `page`'s.
- **Full reindex.** `/settings` → Embedding has a workspace-admin "Re-index everything" action (`enqueueFullReindex`, one `INSERT … SELECT` per entity type with the same pending guard). It runs on the admin connection because an admin's own RLS may not see every team's content. Use it after enabling embeddings on an existing workspace or switching embedding models.
- **Threads are owner-only in RLS.** `ai_thread`'s policy checks `user_id = app.current_user`, not just the workspace; `ai_message` inherits it. Before this, any member who obtained a thread id could read its history (which quotes the owner's team-scoped content) or append to it. `askKompast` throws `AskThreadNotFoundError` for a thread it can't see.
- **No transaction is held while the model streams.** `askKompast(ctx, …)` takes an `AuthContext`, not a `tx`: one short read transaction (credentials, ownership, history, embed + search + enrichment), the model call(s) with no transaction open, then one write transaction (thread if new, both messages with explicit increasing `createdAt` — `now()` is identical within a transaction and history is ordered by it — and one `ai_usage` row with tokens summed across turns). A failed model call persists nothing, not even an empty thread.
- **Claude on Azure AI Foundry** (`azure-foundry-anthropic`) reuses the Anthropic Messages driver unchanged — only the URL (`<endpoint>/anthropic/v1/messages`, endpoint stored in `ai_azure_endpoint` and normalized whether or not it already ends in `/anthropic[/v1[/messages]]`) and auth header (`api-key` instead of `x-api-key`) differ. `ai_model` holds the Foundry deployment name and falls back to the default Claude model ID, which Foundry uses as the default deployment name. API-key auth only; Entra ID bearer tokens are not built this pass. The `ai_provider` column is plain `text`, so the new value needed no migration.
- **Tool calling.** `packages/ai` drivers support tools: Anthropic (`tool_use` blocks, `input_json_delta` streaming) and OpenAI Chat Completions (`tool_calls` by index). Self-hosted OpenAI-compatible servers often reject `tools`, so a 400/404/422 on a request with tools retries once without them and the answer falls back to retrieval only. Ask Kompast's tools (`packages/core/src/ask-tools.ts`): `list_projects`, `list_issues` (status / assignee incl. "me" / sprint incl. "active" / label), `get_issue`, `get_sprint` (with `getSprintReport`), `search_workspace`. Every tool runs in its own `withAuthorizedTenant` transaction as the asking user, so RLS bounds what it can return; errors come back to the model as `{"error": …}`, never thrown. The loop is capped at 5 model turns (`MAX_ASK_TURNS`), and the last turn is sent without tools so the model must answer. `list_issues`' filtering lives in `packages/core/src/issue-query.ts` (`queryIssues`), which MCP `list_issues` now also calls; the REST/MCP resolvers moved there too and throw core `NotFoundError`/`ConflictError`/`InvalidInputError`, mapped to 404/409/400 by `apps/web/src/lib/api-response.ts` and the MCP `tool()` wrapper.
- **Not built:** write tools (Ask Kompast is read-only), burndown/velocity tools, persisting citations for issues found only through tools (citations are the initial retrieval), and any REST/MCP surface for Ask Kompast itself. Text the model streams before a tool call reaches the UI but only the final turn's text is saved.
- **Verified**: real-Postgres tests cover chunking, wholesale chunk replacement, the full enqueue→claim→process pipeline, similarity-ordered search (a deterministic hash-based fake embedding stands in for a real model), and `askKompast`'s end-to-end behavior (retrieval, generation, persistence, citations, thread continuation, the not-configured error). Found and fixed one real bug while writing these: the reindex queue is claimed system-wide, so asserting against `claimPendingReindexTasks(...)[0]` raced other concurrently-running test files — fixed by filtering the claimed batch by a known id instead of assuming position. A real `docker build`+`docker run` confirmed `/api/ask/stream` 405s on GET/401s an unauthenticated POST, and a real issue created against a deliberately-unreachable embedding endpoint produced a genuine DNS failure the worker's reindex queue caught and recorded correctly (proving the failure path since no real embedding credentials exist in this environment).

## Importers

- `packages/import`: extract → map → load, one source folder per importer (`src/jira/`). `fetchJiraIssues()` pages JIRA Cloud's enhanced search, `GET /rest/api/3/search/jql`, following `nextPageToken` until `isLast` (the old `/rest/api/3/search` returns 410 since Atlassian CHANGE-2046; the new one has no `total`); `parseJiraExportFile()` reads the same shape from a checked-out JSON export as a fallback with no live API call. Status/type mapping trusts JIRA's own `statusCategory.key` directly — no human-confirms-the-mapping UI step yet; the dry-run report is the only review surface today.
- A run creates missing statuses/types, creates every issue not already linked via `external_ref` (idempotency key: `(organizationId, "jira", jiraIssueKey)`), backfills parent linkage in a second pass, and — only for issues newly created *this run* — loads comments, worklogs, outward issue links, attachments (if a download callback is supplied), and changelog-derived historical status transitions as backdated `issue_history` rows (deliberately not `moveIssue`, which would also mutate current status). Every issue is wrapped in its own try/catch — one bad issue's error lands in the report, not a killed run.
- **Sprints.** The Sprint custom field's id differs per site, so `extractJiraSprints()` finds it by shape (an array of `{id, name, state}`). Before issues load, every JIRA sprint is planned in order (closed by start date, then active, then future) and created via core's `importSprint` in its real state and dates, skipping `createSprint`/`startSprint`/`completeSprint`, which would stamp today's date and carry issues around. The Kompast number is the one in the JIRA name ("DEMO Sprint 42" → 42) when it's free on the board, otherwise the next free one. If the board already has an active sprint, JIRA's active sprint's issues go into it instead of creating a second active one (a second active JIRA sprint, from parallel sprints, comes in as future). Each issue lands on its open sprint if it has one, else on its last closed sprint if it's done there, else the backlog. Earlier sprints stay as `sprint_issue` history with `removedAt` set to when that sprint closed, so carry-over shows. Closed sprints get a "complete" snapshot and the active one a "start" snapshot. Sprints are idempotent via `external_ref` (`sprint:<jiraId>`, entityType `sprint`). The dry-run report's `sprintMapping` shows the plan. Not handled: a sprint whose JIRA state changed since an earlier import (re-runs don't update it), and story points (no field mapping yet, so imported velocity is 0 points).
- `fixVersions`/`components` land in `issue.customFields.jira` rather than first-class rows — deliberate, not a placeholder; giving them their own management surface is a separate, unscheduled feature.
- `adfToPlainText()` is a best-effort, lossy walk of JIRA's Atlassian Document Format (drops formatting, never throws on an unrecognized node) rather than a strict renderer.
- Every write uses `origin: "import"`, suppressing notifications and automation entirely (importing 5,000 historical issues must not send 5,000 emails or fire live rules).
- Imports run **synchronously in the request** — no background job/queue exists for them; a very large project may exceed a reverse-proxy timeout, a known limitation rather than something this pass builds around.
- Email→Kompast-user resolution: gathers every distinct reporter/assignee/comment-author/worklog-author email across the batch and resolves each once against members before the load pass. No match just leaves the field unset — no directory sync.
- **Verified**: a golden-fixture test (3-issue fixture with a parent/subtask pair, cross-issue link, comment, worklog, changelog transition) against a real Postgres — dry-run writes nothing; a real run creates all 3 issues, resolves the parent link, gets every count right; running the same import twice creates zero duplicates. REST tests mock JIRA's search response for create/dry-run/list/detail/scope-rejection paths. A real `docker build`+`docker run` confirmed the create→run→fail→readable-via-GET lifecycle against a genuinely unreachable host — no real JIRA account exists in this environment to test the success path against a live server, so that rests on the mocked-fetch tests alone.
- **Not built at all**: any background job/queue for long-running imports; a human-confirms-the-status-mapping UI step; a live-JIRA-auth test for attachment streaming; and the fuller reconciliation report the original plan describes (today it's just counts, not "unresolved links, skipped blocks").
- Credentials needed ahead of a real run: JIRA Cloud email + API token. The Notion importer needs none (it reads an export file).

**Notion** (`packages/import/src/notion/`, converter in `apps/web/src/lib/notion-import.ts`, `POST /api/v1/imports/notion`, sidebar dialog `NotionImportDialog`). Works from Notion's own export zip, not the Notion API: that's what a departing team actually has, it needs no integration token or per-page sharing with an integration, and it's one upload.

- **The export format**, as handled: a page is `<Title> <32-hex id>.html|.md`, its sub-pages sit in a sibling folder (`Title <id>/` in older exports, `Title/` in newer ones; both are matched), links between pages are URL-encoded relative paths, and images/files sit in the page's folder. A workspace export is a zip inside a zip, and big ones are split into `Part-N.zip` files that share one folder tree, so nested zips are unpacked in place. Markdown exports write each database twice (`<name> <id>.csv` for the current view, `<name> <id>_all.csv` for every row); `_all` wins, and links to the view CSV still resolve. HTML is the better format: it keeps page icons, toggles and callouts, which the Markdown export drops or leaves as raw `<aside>`.
- **Who can import where.** `requirePageImportTarget` (packages/core/src/import.ts): Workspace docs need workspace owner/admin or the super admin, Private needs only membership. That's stricter than creating a single Workspace page (any member can), on purpose: a bulk import fills everyone's sidebar. Private pages are created with `privateOwnerId` = the caller, and RLS refuses anyone else's Private space anyway. Team/project spaces aren't offered as targets yet.
- **Idempotency** is per target space: `external_ref.source_id` is `workspace:<notionId>` or `private:<userId>:<notionId>`. Re-importing into the same space skips pages that are still there (never overwrites them: someone may have edited them, or have them open). Importing into another space, or by another person, makes an independent copy, because the original may be invisible to them. A trashed or deleted page comes back on re-import.
- **Content.** The extractor and loader stay free of jsdom, like the rest of packages/core and packages/import (see "REST API + MCP"); the loader takes the converter as a callback, the same way the JIRA loader takes `downloadAttachment`. The converter rewrites Notion markup BlockNote doesn't know into HTML it does (`ul.to-do-list` → checkboxes, `figure.callout` → quote with the icon, KaTeX → a LaTeX code block, bookmarks → links, column layouts flattened), then `tryParseHTMLToBlocks`/`tryParseMarkdownToBlocks` → `blocksToYDoc`. Content is written straight into `ydoc_state` only for pages created in the same transaction, so no collab session can be open on them (same reasoning as `seedPageContentFromMarkdown`). Links to other imported pages go through a placeholder `https://kompast.invalid/notion/<id>` href and become `mention` inline nodes plus `link` rows (`syncPageMentions`), so backlinks work from the start. Pages are created parents first, siblings in the order their links appear in the parent, each in its own savepoint; a page whose content fails to convert is still created (empty) so links to it resolve, and the error is in the report.
- **Images and files** referenced by a page are stored at `page-assets/<pageId>/<random>-<name>` and the doc points at `/api/page-assets/<pageId>/<name>`, which checks the reader can see the page on every request, then redirects to a short-lived storage URL. A page's files are exactly as private as the page. The local storage driver serves them with a type from the extension and a sandbox CSP, since an SVG on the app's own origin could otherwise run script when opened directly.
- **`import_run.project_id` is nullable now** (migration 0037). A Notion run has no project, so the RLS policy shows a project-less run only to whoever started it: a Private import's report lists page titles nobody else may see.
- **Limits.** Synchronous in the request like JIRA, so capped at 200 MB per upload and 2,000 pages per import (`MAX_NOTION_PAGES`); a bigger workspace imports part by part. If the load transaction fails after files were uploaded, those objects are orphaned (no cleanup sweep yet, same as issue attachments). The editor itself has no image upload yet, so imported images are the only page assets today.
- **Lost in conversion:** text/background colors, column layouts (flattened into one column), synced blocks (Notion inlines them in the export anyway), database views/filters/property types (a database becomes a static table page plus its rows as sub-pages; each row's properties stay at the top of its page, as a table from an HTML export's header or `Name: value` lines in Markdown), page cover images, comments, page history, and user mentions (kept as plain `@Name` text: there's no email in the export to match people by). Embeds come through as links. Guest share links (`/s/:token`) don't show imported images, since the asset route needs a signed-in reader.
- **Not built:** importing into a team or project space; the Notion API path (live sync / incremental re-import); MCP surface (a zip upload doesn't fit a tool call).
- **Verified**: extractor unit tests on hand-built HTML and Markdown exports (nested zip, both folder namings, `_all.csv`, sibling order, notion.so URLs); real-Postgres loader tests (target permissions, Private tree invisible to other members and the run invisible too, mention backlinks, re-run skips, trashed page comes back, per-space/per-person copies, dry run, a failing page); converter tests decoding the stored Yjs back to blocks; and REST tests for both routes (403 for a member targeting Workspace, asset 302 for the owner and 404 for another member, path traversal refused, bad zip → 422 with the run marked failed). **Not verified** against a real Notion export from a live workspace: the fixtures follow Notion's documented layout, but Notion changes the export's details from time to time, so a real export is the first thing to try.

## JIRA migration

Wizard, background runner, catch-up sync and completeness check. Code: `packages/import/src/jira/` (`migration-runner.ts`, `load.ts`, `reconcile.ts`, `enrich.ts`), `packages/core/src/jira-migration.ts`, and the wizard in `apps/web/src/components/board/jira-migration/`.

- **Paging.** `GET /rest/api/3/search/jql` pages with an opaque `nextPageToken`. A saved token JIRA rejects (400) twice in a row restarts the project from page one. Reloading is safe: every issue is idempotent by `external_ref`.
- **Lease and lock.** A tick holds `jira_migration.lease_expires_at` (5 min), renewed after every page. The BullMQ job's lock is 10 min, longer than a tick's 4-minute budget, so a slow page can't let a second worker claim the same migration.
- **Savepoints.** Each issue, comment, worklog, link, attachment and watcher write runs in its own savepoint. A failing write becomes one entry in the run's `errors`; the page still commits.
- **Former members.** A person the mapping marks "former" gets a `user` row with an `@former.invalid` email, no account and no membership. It is found by JIRA account id through `external_ref`, so a re-run reuses it.
- **Inline media.** Images are matched to attachments by filename, then by position in the rendered HTML. When the count or the dimensions disagree, the media stays unmatched and becomes an "Attachment not found in JIRA" note. A guess would put the wrong file in the body.
- **Attachment URLs.** A stored copy is served at `/api/issue-attachments/<attachmentId>`, and inline references are rewritten to it, so the URL survives a re-copy.
- **Time zones.** JQL reads dates in the JIRA account's own zone, not UTC. The sync formats its `updated >=` cutoff with `Intl` in the zone `/myself` returns, with a 10-minute overlap.
- **History.** A sync's history comes only from the changelog, written with `recordHistory: false`, so an edit is recorded once. Rows are deduped by (field, time, new value).
- **RLS `exists` vs `in (select …)`.** The `issue_comment`, `worklog` and `issue_history` policies use a correlated `exists` against `issue`. The uncorrelated `issue_id in (select id from issue …)` re-scanned the whole issue table on every insert, which made imports quadratic on real data (`packages/db/rls.sql`).
- **Reconciliation is read-only.** It reads JIRA with a fixed field list plus the Sprint and mapped fields, and compares a page at a time with one query per table. Each difference is explained by a code (`explained:edited-in-kompast`, `not-migrated`, `deleted`, …) or is `unexplained`. `clean` means none are unexplained.
- **Reconciliation limits.** Watcher lists are fetched for at most 300 issues per run; past that, a gap is reported as unverified. Inline media is counted, not matched one-to-one, because external media and rewritten links make the two sides differ by design. The current sprint is computed from Kompast's sprint rows, since the loader's plan order isn't kept after a run.
- **Reconciliation cursor.** The run's cursor carries its differences (up to 20,000) until it finishes. A large project's cursor is large while the check runs.
- **Finish.** Refused without a completeness check newer than the last sync, and with unexplained differences unless they are acknowledged. It clears the token and turns auto-sync off in one transaction.
- **Not built.** Comment threads: JIRA's API has no thread structure to import, so replies come in as flat comments. Development and plugin fields (the Development panel, Tempo, and similar) are not migrated. Linking a former member to a Kompast user after they join is not built; ask an admin. Multi-workspace sign-in picks no workspace.

## Security hardening (Nov 2026 pass)

**Outbound requests to user-chosen URLs** go through `guardedFetch` (`packages/core/src/net-guard.ts`): automation webhooks, the JIRA client (legacy import + migration), and legacy JIRA attachment downloads. Private/loopback/link-local/CGNAT/multicast and the IPv6 forms that embed them are refused; hostnames are checked **at connect time** in an undici `Agent` `lookup` (every resolved address must pass, and the socket connects to that vetted address — no DNS-rebinding window), IP literals before sending. Redirects are never followed. `OUTBOUND_ALLOW_PRIVATE_HOSTS` exempts named hosts (on-prem JIRA); link-local never. Tests stub `globalThis.fetch`, so the connect-time lookup doesn't run there — `net-guard.test.ts` exercises it against `*.localtest.me` (public DNS → 127.0.0.1). Verified that the npm `undici@7` Agent works as a dispatcher for Node 22's built-in fetch (the Docker base). **Not guarded:** AI/embedding provider base URLs — deployment-admin only, and self-hosted model servers on private IPs are a legitimate setup.

**Rate limits** (`apps/web/src/lib/rate-limit.ts`, Redis fixed window, fail-open on Redis errors): bad API tokens 30/min per IP (checked before verifying), 600 req/min per PAT (REST + MCP via `requireApiAuth`), AI and Ask streams 30/min per user, share-link password attempts 10/15 min per link+IP, `/setup` 10/15 min per IP. Client IP is the first `X-Forwarded-For` entry — trustworthy only behind the documented Caddy setup (Caddy overwrites a client-sent XFF); requests with no XFF skip the per-IP limits rather than share one bucket.

**Size caps:** uploads 100 MiB (`MAX_UPLOAD_BYTES`, bound into GCS signed URLs via `x-goog-content-length-range`, counted while streaming for local storage); Notion import 1 GiB uncompressed / 50,000 entries across nested zips, and a missing `Content-Length` is a 411; AI inputs `.max()`-bounded; collab WebSocket frames 5 MiB. Collab refuses the WebSocket handshake (403, in `onUpgrade`) unless `Origin` is `APP_URL`'s origin. Share-link passwords use async scrypt (no event-loop blocking). AI stream errors no longer echo provider error bodies to the client.

**HTTP headers and CSRF (`apps/web/src/start.ts`).** A global request middleware sets security headers on every response the app serves (pages, server functions, `/api`), so a bring-your-own-proxy deploy still gets them; a header a route already set (the sandbox CSP on storage downloads) wins. Enforced CSP is only the non-breaking part (`frame-ancestors 'self'; object-src 'none'; base-uri 'self'; form-action 'self'`); the full source allow-list ships as `Content-Security-Policy-Report-Only` until it has been checked in a real browser against every editor feature — then promote it. `script-src` still needs `'unsafe-inline'` for TanStack's inline hydration scripts; a per-request nonce (router `ssr.nonce`) is the follow-up. **Gotcha:** defining `src/start.ts` at all removes TanStack Start's *default* server-function CSRF middleware (`createStartHandler`: `startInstance ? startOptions.requestMiddleware : [defaultCsrfMiddleware]`) — `csrfMiddleware` is listed explicitly first; don't drop it. Verified: a cross-site server-function POST gets 403.

**Guest share HTML** is sanitized server-side (`apps/web/src/lib/share-html.ts`, DOMPurify on a jsdom window) before the share page injects it. Links keep only http(s)/mailto hrefs (relative/internal links become plain text for guests) and get `rel="noopener noreferrer"`.

**`/setup` lockdown.** Besides "refuses once Entra is configured": refused in DEMO_MODE, refused once any user exists (unless local dev login is on), rate-limited per IP, and — when `SETUP_TOKEN` is set (install.sh generates and prints one) — the form must include it. `ENABLE_DEV_LOGIN=true` now refuses to boot unless `NODE_ENV` is set explicitly (an unset one used to default to development).

**Containers.** Collab and worker images use `pnpm deploy --prod` like web (724/731 MB → 230/270 MB, dev tooling gone); migrate and seed run as a non-root user. Compose adds `no-new-privileges`, `cap_drop: ALL`, memory/pid limits, log rotation and healthchecks (worker has none — no port to probe). Redis requires a password (`REDIS_PASSWORD`; `REDIS_URL` carries it) — **an existing `infra/.env` without `REDIS_PASSWORD` won't start Redis until it's added**; `install.sh upgrade` adds the pair automatically. CI has least-privilege `permissions`, SHA-pinned actions, a `pnpm audit --prod --audit-level=high` gate, a Trivy scan in release, and Dependabot (npm, actions, docker).

**Database role split.** Three roles: `kompast_admin` (owner/superuser — `DATABASE_ADMIN_URL`, only the `migrate` service gets it; compose blanks it and `POSTGRES_PASSWORD` for web/collab/worker via the `x-app-db-env` anchor), `kompast_app` (`DATABASE_URL`, RLS-subject, every normal request) and `kompast_service` (`DATABASE_SERVICE_URL`, behind `adminDb`: `BYPASSRLS` + data-only grants, `nosuperuser nocreatedb nocreaterole`). `bootstrapServiceRole` (`packages/db/src/bootstrap-roles.ts`) refuses a service URL whose user is also the app or admin user — BYPASSRLS on the app role would silently disable every policy. `adminDb` falls back to `DATABASE_ADMIN_URL` when no service URL is set (dev, tests). Verified: the whole test suite passes with `adminDb` as `kompast_service` (CI now runs that way), the role can't run DDL or `pg_read_file`, and a real compose stack — fresh, and upgraded from a pre-split `.env` via `add_missing_runtime_secrets` — comes up healthy with no admin credentials inside the app containers. Managed Postgres that can't grant `BYPASSRLS`: set `DATABASE_SERVICE_URL` to the admin URL (old behavior).

**Security backlog (found, deliberately not done in this pass):**
- Installer / `kompast upgrade` run `curl | bash` from `main` as root; `IMAGE_TAG` defaults to `latest`. Pin to release tags with checksums; digest-pin base images.
- Automation webhooks still run inside the step's DB transaction (bounded by the 10 s timeout); move the call outside it.
- GCS download URLs keep the stored Content-Type inline (driver interface has no filename/type) — add `responseDisposition: attachment` for non-images.
- `BETTER_AUTH_SECRET` doubles as AES key and collab/storage HMAC key — derive per-purpose keys (HKDF).
- No-RLS tables with id-only writes: `saved_view` update, board-column `boardId`/`projectId` mismatch, `issue_watcher`; workspace-only RLS on notification/automation-run tables.
- Restricted-page inheritance for sub-pages; PAT expiry + the unused `admin` scope; Entra `pkce`; CSV export `\t`/`\r` formula prefix; attachment `sourceUrl` open redirect; encrypted backups; `read_only` root filesystems; CSP nonce + promoting the Report-Only policy; Trivy scans after push (a failing scan doesn't stop the image from being published).
- Test infra: `packages/import` has an intermittent cross-file race ("the migration was not claimed" / 10 s timeouts under full parallel load); each file passes alone.
